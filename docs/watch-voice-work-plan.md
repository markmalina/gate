# План работ по голосовым записям с часов

Дата: 25 октября 2026 года. Статус: план подготовлен, реализация этим документом не запущена.

**Цель:** Марк нажимает Stop на часах; после загрузки в Dropbox запись автоматически появляется полным текстом в приватном Inbox mark. Для каждого файла видны текущий этап, задержка, ошибка и расход. Work для обработки не нужен.

Продуктовая задача — [#736](https://github.com/markmalina/gate/issues/736), исходный маршрут — [#731](https://github.com/markmalina/gate/issues/731). Существующий кандидат постоянного обработчика — [PR766](https://github.com/markmalina/gate/pull/766). Аудит и этот план сохраняются в документационном [PR768](https://github.com/markmalina/gate/pull/768).

Основание — [аудит 25 октября](audit/2026-10-25/voice-and-project-audit.md). Его числа 28 файлов / 10 готовых / 18 ожидающих и задержка 14:55 по медиане относятся к срезу 19:03 МСК с контрольной проверкой 19:13. Они не заменяют новую сверку при начале исполнения. При подготовке плана подтверждены открытый PR766 и неизменившийся main; новый аудит очереди не выполнялся.

## Фокус и границы

Работаем по маршруту Galaxy Watch → Samsung Recorder → телефон → Dropsync → Dropbox /Alpha/Voice → Gate → OpenAI → private mark Inbox.

Приоритеты по порядку:

1. Видеть судьбу каждого файла и разобрать текущий остаток.
2. Видеть остановку процесса, возраст очереди и стоимость.
3. Убрать ожидание GitHub Actions и ограничение одной записи за запуск.
4. Запускать обработку по событию с резервной проверкой.
5. Проверить передачу с часов, сократить расходы и оставить один понятный процесс.

Общий рефакторинг Gate, MTProto, Rich, Beta, AQUB и другие продукты в этот план не входят. Исправления общих компонентов допустимы только когда конкретно блокируют Voice, с отдельным ограниченным diff. Потоковая расшифровка во время диктовки — отдельный последующий этап; сначала доводим существующую файловую цепочку.

## Критерии результата

| Область | Критерий приёмки |
| --- | --- |
| Учёт | Для 100% доступных файлов в разрешённом диапазоне есть исходная ревизия, запись Gate и результат либо явная причина отсутствия результата. Пропуски и исключения не маскируются счётчиком «успешно». |
| Полнота | В Inbox доставляется полный текст; если он разбит на комментарии, все части подтверждены. Сохраняются оригинал и его хеш. |
| Повторы | Повторное событие, запуск и восстановление после рестарта не создают повторный STT или публикацию для той же операции. Новая Dropbox revision явно отличается от повтора. |
| Обнаружение | При свободном worker: сначала P95 Dropbox server_modified → начало обработки ≤35 секунд при polling 30 секунд; после webhook целевой P95 ≤5 секунд от принятого события до начала обработки. |
| Конечная задержка | Начальная цель для аудио до 3 минут, при свободном worker и нормальной сети: P95 Dropbox → полный Inbox ≤90 секунд. Длинные файлы и пакеты измеряются отдельно. |
| Пакеты | Никакого ожидания следующего cron между готовыми заданиями. Контрольный пакет из 20 источников полностью сверяется, его время измеряется; число файлов само по себе не даёт универсального SLA без длительности аудио. |
| Надёжность | Сбой одного файла или неизвестная публикация не блокирует остальные записи. После восстановления внешнего сервиса очередь продолжает допустимую работу. |
| Стоимость | Для каждой записи и дня видны длительность, модель, фактический учёт, резерв и неопределённый расход; бюджет проверяется до provider I/O. |
| Работа без Work | После выпуска процесс работает при закрытом Work. Не менее суток наблюдения и отдельная проверка рестарта. |

Все пороги выше — цели, а не уже измеренные свойства. Для P95 указывать число записей, окно, длины аудио, условия и исключения. До 30 реальных подходящих наблюдений показывать предварительную статистику, а не объявлять SLA доказанным. Медленные и ошибочные задания остаются в отчёте отдельными строками.

## Этап 1 Учёт каждой записи и сверка остатка

**Результат:** есть один доступный владельцу список «что записано, где находится и почему ещё нет текста».

- [ ] W01. Обновить read-only снимок Dropbox, Gate, Inbox и текущего driver. Сверить файлы контрольного дня, включая уже опубликованные после аудита. Не повторять распознавание ради сверки.
- [ ] W02. Добавить в существующую защищённую поверхность Gate постраничный inventory Voice с фильтром по периоду, состоянию и event ID. Сначала API/табличная выдача; отдельный новый сайт не нужен.
- [ ] W03. Дать каждой доступной ревизии однозначную строку: файл, источник, event ID, состояние, длительность, возраст, результат или причина. Выделить источники, не попавшие в Gate, и расшифровки без полной доставки.
- [ ] W04. Связать запись с имеющимися billing reservation и usage entries; для сегодняшнего дня получить отдельный итог, если эти данные действительно сохранены. Старые отсутствующие метки не восстанавливать предположениями.

### Поля карточки записи

| Группа | Что показывать |
| --- | --- |
| Источник | Имя, Dropbox file ID/revision, event ID, хеш, размер, длительность; значения доступны только в owner scope. |
| Время | Dropbox server_modified, first_seen_at, archived_at, queued_at, processing_started_at, normalize start/end, provider start/end по попыткам/частям, transcript_saved_at, publish start, final delivered_at. |
| Состояние | Отдельно приём/архив, STT и доставка. Очередь, активная работа, успешное завершение, определённый отказ и unknown различимы. |
| Результат | Ссылка на issue, ожидаемое/подтверждённое число частей, последняя безопасная категория ошибки и следующий допустимый шаг. |
| Деньги | Модель, usage, settled/reserved/unknown с единицами валюты, provider attempt count; отсутствие данных обозначено явно. |

Новые поля — предложение аддитивной схемы либо совместимой проекции существующих данных. Не заменять этим списком реальные storage enum вслепую. Раздельные фазы должны сохранять различие «текст уже готов» и «текст доставлен».

Времена хранить с UTC offset, показывать МСК явно. День загрузки, предполагаемая дата в имени и подтверждённое время записи — разные поля. Stop на часах и появление на телефоне остаются неизвестными, пока их не измерили на устройстве.

**Проверка:** все источники выбранного диапазона имеют объяснимый исход; точные пары file ID/revision совпадают; итоги по строкам совпадают с агрегатами; частичная публикация не считается полной. Неподтверждённая сумма не называется списанием OpenAI.

**Оценка:** 1–1,5 инженерных дня, без новой подписки. Если безопасного runtime чтения ещё нет, сначала подготовить узкое read-only наблюдение через текущий Gate-owned Ops маршрут; не обходить его через извлечение секретов или provider UI.

## Этап 2 Мониторинг процесса и задержек

**Результат:** по одному статусу понятно, работает ли обработчик, движется ли очередь и где расходуется время.

- [ ] W06. Добавить агрегаты: обнаружено/сохранено/в очереди/обрабатывается/STT готово/частично опубликовано/доставлено/rejected/unknown; возраст самого старого задания; глубина и изменение очереди; время и число последних успешных доставок.
- [ ] W07. Считать задержки отдельных фаз, длительность аудио и отношение времени обработки к длительности; показывать P50/P95/max, объём выборки и ошибки. Не смешивать время очереди со временем OpenAI.
- [ ] W08. Добавить runtime-сигналы о конкретной неисправности и восстановлении с дедупликацией по инциденту. Использовать общий мониторинг Gate и существующий отчёт Center; отдельный ChatGPT heartbeat и новую регулярную автоматизацию не создавать.

### Первоначальные сигналы

| Сигнал | Предлагаемый порог и действие |
| --- | --- |
| Очередь есть, driver не работает | Нет цикла более 2 минут в новом постоянном режиме → fault; показать последнюю ошибку и длительность простоя. К старому Actions этот порог не применять. |
| Сканирование источника остановилось | Нет успешного сканирования более двух резервных интервалов, но не менее 3 минут → degraded. Указать, что полнота списка Dropbox неизвестна. |
| Возраст очереди растёт | Старейшая запись ждёт больше 5 минут и возраст не снижается в двух измерениях → warning; отдельно различать большой пакет и отсутствие прогресса. |
| Обработка превышает разрешённый срок | Срок считать из числа частей, timeout и lease конкретного задания. Не ставить универсальные 2 минуты для часового аудио. |
| Неопределённый исход | Новое provider/delivery unknown → один инцидент, требующий сверки; не повторять внешний эффект автоматически. |
| Бюджет | 70% / 90% / 100% внутреннего потолка: прогноз, предупреждение, подтверждённая остановка до provider call. Это не измерение баланса API. |
| Устранение | Закрыть тот же инцидент при выполнении условия восстановления; не плодить новые issues/сообщения на каждый цикл. |

Нет новых файлов и очередь пуста — нормальный простой, а не ошибка «давно не было расшифровки». Отправку уведомлений во внешний канал включать только через уже согласованный маршрут; подготовка мониторинга сама по себе не создаёт новых рассылок. В общих логах нет имён файлов, текста, audio bytes и ключей; детальная карточка остаётся приватной.

**Проверка:** синтетически остановленный worker, недоступный Dropbox, устаревшие метрики, исчерпанный бюджет и обычный ночной простой дают разные состояния. Повтор одного fault не создаёт повторные уведомления; восстановление видно.

**Оценка:** около 1 дня, переиспользуя существующие health/status и хранилище метаданных.

## Этап 3 Ускорение без ожидания Actions

**Результат:** один постоянный обработчик выбирает доступную работу подряд, без нового runner на каждый файл.

- [ ] W09. Продолжить существующий PR766, сохранив все принятые исправления. Добавлять только необходимые для Voice диагностику и интеграцию; не создавать конкурирующий продуктовый PR.
- [ ] W10. Установить фактические условия выпуска: точный source/startup/predeploy/schema, writer с доступом только к private mark и Issues write, один активный driver, бюджеты и rollback. Старые потраченные диагностические grants не запускать повторно.
- [ ] W11. Сначала использовать polling 30 секунд. При непустой очереди продолжать ограниченные партии без обязательного sleep между каждым готовым заданием. Вначале последовательный STT; параллелизм вводить только если измерения докажут необходимость и позволяют лимиты.
- [ ] W12. Разделить сбой чтения Dropbox и обработку уже сохранённых файлов: недоступность Dropbox не должна останавливать разрешённую работу с локальным архивом. Unknown одного outbox не должен держать всю очередь.
- [ ] W13. При переключении сохранить исходники, cursor, future-only watermark, provider claims и GitHub receipts. Старый Actions путь выключать как обработчик в том же управляемом переходе; два writer не работают одновременно. Никакого reset cursor или молчаливого исторического backfill.

Ошибки источников локализовать: слишком большой/повреждённый файл фиксируется как отдельная диагностируемая проблема; другие допустимые файлы продолжают поступать. Это не расширяет лимиты и не разрешает скачивать файл сверх текущего bound.

**Проверка:** до выпуска — детерминированные проверки и один необходимый CI точного head; после выпуска — фактическая ревизия/health и ограниченная приёмка новых разрешённых записей. Проверить одиночный файл, пакет, дубли, рестарт и остановку одного внешнего сервиса. Старые записи не распознавать повторно для доказательства скорости. Откат сохраняет схему и журналы.

**Оценка:** 1–2 инженерных дня после получения нужных эксплуатационных доказательств. Время внешних блокировок отдельно от трудоёмкости. Новый сервер не предполагается; дополнительный CPU/DB расход измерить. Главный денежный эффект — убрать пустые polling jobs Actions.

## Этап 4 Обработка по событию и резерв

**Результат:** загрузка в Dropbox будит тот же постоянный worker; потеря события не теряет файл.

- [ ] W14. Расширить существующий подписанный Dropbox webhook: быстро сохранить durable pending для Voice, затем разбудить worker. Не выполнять STT внутри HTTP webhook и не ставить GitHub Actions обратно в критический путь.
- [ ] W15. Использовать тот же Voice cursor и общую очередь, с блокировкой/lease против дублей. Сигнал в памяти — ускоритель; после рестарта восстановление идёт из durable state.
- [ ] W16. Оставить резервный delta scan раз в 60 секунд. После наблюдения разрешить 1–5 минут, если устраивает верхняя задержка при потере webhook. Для пакетов начать с короткого debounce 1–3 секунды.

**Проверка:** одинаковое событие десять раз, события не по порядку, потерянное событие, рестарт между получением и обработкой, пакетная загрузка. Пропущенное событие догоняется резервом в пределах одного интервала плюс время текущего цикла; источники и внешние эффекты не дублируются.

**Оценка:** 0,5–1 дня. Целевой выигрыш после этапа 3 — оставшиеся секунды обнаружения и меньше пустых Dropbox запросов. Если polling уже выполняет пользовательскую цель, этот этап допустимо отложить по измеренному эффекту.

## Испытания восстановления

| Сценарий | Ожидаемый результат |
| --- | --- |
| Телефон без сети, затем загрузка | Все фактически загруженные файлы учтены; время до Dropbox отделено от Gate. |
| Dropbox временно недоступен | Сканирование degraded, уже сохранённые разрешённые задания продолжаются; cursor догоняет после восстановления. |
| OpenAI определённо отказал | Причина записана; нет бесконечного STT retry. Допустимый recovery явно указан. |
| Ответ OpenAI неизвестен | Unknown и сохранённый резерв/история, ноль слепых повторов. |
| GitHub не принял текст | Готовый transcript остаётся, повторное распознавание не требуется. |
| GitHub принял текст, подтверждение потерялось | Сверка точной публикации, не второй POST; остальные задания продолжают работу. |
| Worker рестартовал или запущен дважды | Одно владение заданием и не более одного внешнего эффекта; живой lease не объявляется мёртвым соседним процессом. |
| Один файл превышает лимит | Отдельная явная причина, без молчаливого пропуска и блокировки следующих файлов. |
| Бюджет достигнут | Provider call не начинается; видно, почему очередь ждёт. |
| Длинный текст разбит на комментарии | Запись delivered только после подтверждения всех частей; полный текст собирается без обрезки. |

Fault injection выполнять на локальных/стендовых fixtures. Реальные provider проверки ограничить точными разрешёнными файлами, числом частей и бюджетом текущего исполнения. Автоматические повторы неопределённых STT/публикаций не вводятся. Смена модели, credentials, оплата и очистка истории не являются побочными действиями теста.

## Порядок исполнения и отчёт

| Очерёдность | Что завершить | Выходной материал |
| --- | --- | --- |
| 1 | W01–W04 | Сверка остатка и карточки записей с причинами/стоимостью. |
| 2 | W05–W08 | Наблюдаемые queue/worker/latency/budget, проверенные сигналы. |
| 3 | W09–W13 | Один постоянный driver, пакетная обработка, замер до/после. |
| 4 | W14–W16 | Webhook с резервом, если его выигрыш нужен после замера. |
| 5 | W17–W22 | Замер устройства, расходы, восстановление и актуальный runbook. |

Работу с устройством можно провести при удобном доступе к часам, не дожидаясь webhook. При внешнем блокере выпуска продолжать inventory, локальные fixtures, стоимость и документацию; не занимать compute lease ожиданием и не заявлять, что worker исправлен.

Ориентир: **4–7 инженерных дней**, без времени внешних блокировок, плюс минимум сутки наблюдения после выпуска. Первые результаты — сверяемый остаток и прозрачная очередь, а не завершение всей платформы Gate. Оценка не обещает календарную дату.

Отчёт по завершении каждого содержательного этапа: что изменилось; точные source/runtime revision и время; сколько файлов пришло/готово/ждёт/ошибочно; P50/P95/max и размер выборки; расходы и резерв; доказанная проверка; следующий шаг или конкретный блокер. На неизменном состоянии не делать коммиты/пустые отчёты.
