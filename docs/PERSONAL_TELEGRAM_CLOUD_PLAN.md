# MTProto: полный облачный маршрут AI → Gate → Telegram
Дата: 11.10.2026. Владелец результата: α Gate. Поручение и приёмка: Марк. Каноническая задача: #696.

## Цель и уточнение владельца
Марк поручил довести маршрут до работающего результата и составить полный план. Требуемая среда — облако; Windows и постоянно включённый компьютер владельца не являются требованиями. Историческая запись 21 июля о завершённом Windows enrollment не является свежим доказательством существования файлов. Марк не подтверждает такую локальную настройку; возможно, было только создано API-приложение. Приложение заново не создавать без установленной причины.

Рабочий результат: AI получает доступные операции через Gate MCP/API; Gate выполняет их через пользовательскую MTProto-сессию владельца и возвращает проверяемый результат. Telegram Web не участвует. Права ограничены возможностями Telegram, аккаунта и конкретного чата.

## Облачная архитектура
Текущий Gate хранит команды, привязки и receipts. Один выделенный Python/Telethon worker для каждой разрешённой пользовательской сессии владеет соединением с Telegram; web-реплики не конкурируют за сессию. Worker получает команды через защищённый внутренний путь/очередь с actor, workspace, account, session и peer scope. Статус формируется по последней ограниченной проверке с временем и актуальной ревизией.

Переиспользовать Gate PostgreSQL и существующий delivery fence; SQLite-журнал нельзя переносить в эфемерный диск контейнера как единственное production-доказательство. Сессия и кэш access_hash шифруются; ключ отдельно в защищённой конфигурации, устойчивое хранение и ротация проверяются. Точное место хранения и вариант очереди закрепить после проверки текущего Gate/Ops контракта. Новый платный сервис без согласованной стоимости не создавать.

## Этапы и критерии
### 1. Облачная конфигурация и диагностика
Добавить cloud binding и диагностику: наличие api_id/api_hash, привязки владельца, зашифрованной сессии, ключа, валидность расшифровки; наружу только состояния, не значения. Установить pinned Telethon в нужный runtime. Отделить configured от authenticated, временный probe от работающего worker. Готовность не наследовать от Bot API.
Приёмка: корректные состояния absent/incomplete/invalid/prepared; без сетевых вызовов, вывода секретов и ложного connected=true.

### 2. Защищённое подключение аккаунта
Сначала ограниченно проверить существующую облачную сессию. При её отсутствии подготовить owner-authenticated setup-поверхность: ввод существующих API-параметров, QR-вход либо телефон/код; при необходимости 2FA. Не вводить их через AI чат/MCP/logs. QR/код имеют TTL, повтор ограничен, временные данные очищаются, успешная сессия сразу шифруется. Проверить точный owner через get_me и внутреннюю Account/PersonIdentity-привязку; разные RU/BY аккаунты не угадывать.
Приёмка: сессия нужного владельца авторизована; переживает restart; параметры не возвращаются в ответах; отзыв сессии обнаруживается. Человек нужен только для входа, когда действующей сессии нет.

### 3. Worker, очередь, управление и развёртывание
Реализовать один активный consumer/session lease, bounded timeouts, graceful shutdown, запись heartbeat состояния по фактическому соединению, catch-up/checkpoints и controlled reconnection. У read retry и mutation retry разные правила. Добавить pause/resume/disconnect и отзыв локальных разрешений; logout/revocation требуют точного действия владельца. Согласовать Gate-owned Ops contract для configure/inspect/release и нужных миграций. Не использовать замороженный AQUB и его credentials.
Приёмка: worker переживает deploy/restart, вторая реплика не получает параллельное владение; Gate видит конкретную причину неготовности. Развёрнутая ревизия и rollback проверены через текущий Gate-only Ops маршрут.

### 4. Поиск, адресаты, диалоги и чтение
Добавить список доступных диалогов с пагинацией, поиск по названию/username/ссылке, отдельный поиск доступных публичных сущностей, account-specific resolution, типы user/basic-group/supergroup/channel/Saved Messages. Находить среди доступного аккаунту; не обещать поиск закрытых недоступных групп. При неоднозначности дать варианты; выбор фиксирует peer_ref, provider id и access_hash внутри Gate.
Добавить историю по дате/окну/количеству, поиск текста в выбранном чате, reply/thread/media metadata. Ограничивать страницы/байты, возвращать источник/даты/continuation. Читать статус отдельно от намеренного mark-read: изменение статуса не скрывать. Не выгружать весь аккаунт для каждого запроса.
Приёмка: реальные результаты и текст из выбранного доступного чата, корректная пагинация, ответ на поиск; другой аккаунт/peer не подставляется.

### 5. Личная отправка, первое исходящее и изменения сообщений
Подключить существующий sender к AI-командам. Добавить новый исходящий диалог без предыдущего inbound/reply task; расширить общий fence на logical command/draft, сохранив защиту обоих транспортов. Поддержать text/entities, ответ на сообщение, пересылку, edit, delete выбранных сообщений, реакции, pin/unpin; форматирование сохранять предсказуемо.
Любая операция связывает владельца, получателя/чат, объект, содержание и effect; показывать preview. Конкретная команда Марка является разрешением на соответствующее действие, без повторного подтверждения того же действия. Для неясного адресата, массового воздействия или удаления запрашивать точный scope.
Приёмка: личная доставка без входящего сообщения и вне Business window; message receipt; изменённый после разрешения payload не отправляется; replay/concurrency/crash не приводят к новой попытке. unknown требует сверки, не слепого повторения.

### 6. Вложения и медиа
Реализовать download/upload документов, фото, видео, голосовых и альбомов через MTProto; chunked I/O, проверка размера/checksum/MIME, лимиты аккаунта и Telegram, временное защищённое staging с TTL, fetch по точному message/media ref. Большие файлы не считать автоматически безлимитными. Голосовые/видео возвращать как файлы; транскрипция и AI-анализ используют существующий отдельный разрешённый provider path, этот этап не меняет model policy.
Приёмка: отправка/скачивание выбранных файлов, byte-for-byte checksum, корректные подписи/порядок; сбой upload не создаёт дублирующую доставку; приватные ссылки не попадают в общие logs/Git.

### 7. Группы, каналы, контакты и организация аккаунта
Подключить уже существующее создание приватной группы. Добавить проверку результата, открываемую ссылку и дальнейшее управление в пределах прав аккаунта: название/описание/изображение, приглашения/участники/права, join/leave, admin state; отдельно каналы. Приглашения и изменения состава выполняются по точному поручению, не автоматически вместе с созданием.
Добавить контакты, поиск по явно заданному идентификатору, архив/папки, черновики, mark-read/mute/unmute, Saved Messages. Для каждой операции публиковать supported/rights-required/unavailable.
Приёмка: конкретные групповые и организационные сценарии доказаны реальными receipts, private/public scope и права соблюдаются.

### 8. Полнота AI/MCP и фронт
Gate отдаёт обнаруживаемый каталог инструментов и их готовность, описания input/output, bounded errors, operation receipt/status/cancel. AI умеет выбрать операцию и сообщить реальный результат, а не успешное создание очереди. Для длинных задач progress/cancel имеют серверный механизм. Каждый новый Work видит инструменты после обновления схемы подключения.
Приёмка: задачи выполняются из фронта естественными командами, без обхода через Telegram Web; отмена реально останавливает оставшуюся работу.

### 9. Сквозная приёмка и эксплуатация
Детерминированные tests: malformed/expired config, wrong owner/peer, revocation, paging, rights, formatting, file size/hash, concurrency, crashes до/после Telegram, unknown, FloodWait, session revoked, queue replay, retention, missing provider.
Первый live набор после подключения: проверка owner; своё Saved Messages (text/file/edit/delete точных тестовых сообщений); одна выбранная группа/история при допустимом AI data scope; первый исходящий выбранному адресату с точным текстом; одна приватная группа с заданным названием без приглашений. Остальные операции — отдельные bounded fixtures по каталогу, не изменения произвольных реальных контактов.
Финал: exact deployed SHA; fresh runtime status; tools доступны в Work; receipts каждого сценария; restart recovery и rollback; эксплуатационная инструкция. #696 остаётся открытой до фактического результата.

## Реальные ограничения и условия чтения
Не обещать буквально любой Telegram method: возможности аккаунта, права чата, ограничения Telegram/FloodWait и доступность реализации проверяются. Секретные чаты, звонки, платежи, изменение 2FA/удаление аккаунта не объявлять готовыми в стандартном Telethon worker. Операция вне каталога получает точное unsupported или отдельный review, а не общий raw RPC от AI.
Официальные Telegram API terms п.1.5 и content licensing содержат ограничения применения платформенных данных для AI. Исключения могут предоставляться при индивидуальном, информированном и продолжающемся согласии relevant users для конкретного context. Наличие доступа к аккаунту не является автоматически такой лицензией. Поэтому передачу чужих сообщений AI нужно включать только для конкретно допустимого data scope; это не блокирует transport/authentication, owner-command отправку или обычный клиентский доступ.
Источники: https://core.telegram.org/api/terms ; https://telegram.org/tos/content-licensing ; https://docs.telethon.dev/en/stable/concepts/sessions.html ; https://core.telegram.org/api/auth

## Что требуется от Марка и что делает Work
Work самостоятельно выполняет проектирование, код, synthetic tests, подготовку release/ops contract, документацию, инструменты и проверяемые сценарии. Текущие cloud keys/session не запрашивать в чат и не считать отсутствующими без защищённой диагностики.
Марк потребуется для защищённого входа только если существующая сессия отсутствует/недействительна; если параметры приложения нигде не сохранены — ввести их на подготовленной защищённой setup-поверхности. Live-получатель/текст и доступный group/data scope задаются конкретной командой владельца. Другие Gate задачи и проекты в это исполнение не входят.
