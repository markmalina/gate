# Gate MTProto RU · испытание S1 в ChatGPT Work

Владелец принимает S1 в новой сессии Work. Он должен увидеть каталог, подготовить команду, потерять первый ответ, вернуться к той же операции, проверить результат и отменить её. Отдельно он передаёт один публичный контрольный файл и открывает его обратно. У S1 есть журнал и синтетическая привязка RU. За время испытания допускается ровно ноль обращений к Telegram.

[Задача #696](https://github.com/markmalina/gate/issues/696) · [ТЗ v4.0](https://github.com/markmalina/gate/blob/bd923c7f2ed782ea5f098bdee44b3d1b7df9a56e/docs/specs/MTPROTO_RU_SPEC_V4.md)

## Что установить

Отдельный процесс из проверенной ревизии #761. Выделить HTTPS-имя и пустую базу с отдельной ролью на тестовом PostgreSQL. В процессе запускается только фабрика `app.api.personal_stage:create_app`. Приложение открывает свою БД и проверяет привязку до первого HTTP-запроса. Маршруты Business, вебхуки, Telethon и исполнитель Telegram отсутствуют в этой точке входа. Действующие сессии RU и BY для S1 не нужны.

| Настройка | Значение и владелец |
| --- | --- |
| `GATE_ENV` | `staging`. Для автоматизированных испытаний также есть режим `test`. |
| `GATE_PERSONAL_STAGE_DATABASE_URL` | Защищённый DSN выделенной базы в формате `postgresql+asyncpg`. Только для однократной миграции передать тот же DSN как `DATABASE_URL` в окружение процесса Alembic. |
| `GATE_PERSONAL_STAGE_MASTER_KEY` | Сохранённый между перезапусками случайный ключ Fernet. Из него независимо выводятся ключи текста, полномочия и ссылки на получателя. |
| Префикс `GATE_PERSONAL_STAGE_` и поля `RESOURCE`, `ISSUER`, `JWKS_URL`, `CLIENT_ID` | HTTPS-адрес стенда с путём `/mcp`, точный issuer, его HTTPS JWKS и отдельный OAuth-клиент Work. Audience токена совпадает с адресом стенда. |
| `OWNER`, `WORKSPACE`, `BINDING_ID` с тем же префиксом | Точное значение `sub` владельца, подписанный workspace и отдельный UUID синтетической установки. В account IDs должен быть RU UUID Gate. |
| `GRANT_ID`, `GRANT_EXPIRES_AT`, `APPROVAL_REF` | Отдельный UUID полномочия, абсолютное время окончания с часовым поясом, ссылка-идентификатор согласованного испытания. При перезапуске все три значения сохраняются. |
| `WORKSPACE_CLAIM`, `ACCOUNT_IDS_CLAIM`, `PROJECT_IDS_CLAIM` | Имена подписанных claims. По умолчанию `gate_workspace_id`, `gate_account_ids`, `gate_project_ids`. При использовании Auth0 Action указать точные имена из тестовой конфигурации. |
| `FILE_HOST` | Один проверенный HTTPS-хост вложений Work, отдельный от адреса Gate. По умолчанию импорт файла выключен. В переписку и логи достаточно записать домен и код ошибки, подпись ссылки содержит секрет. |

В Auth0 зарегистрировать тестовый resource и три разрешения. Выдавать их только согласованному владельцу и клиенту. Привязка использует подписанные issuer, `azp` или `client_id`, subject, workspace и RU account ID. Указанные клиентом поля аргументов не создают полномочий. Секрет клиента хранится в настройках OAuth-подключения Work. Gate проверяет подписи по публичным ключам. [Схема подключения Auth0](../MCP_CHATGPT_AUTH0_RUNBOOK.md)

Для отдельного сервиса Railway указать **Config File Path** `/railway.personal-s1.toml` и проверить в предпросмотре команду `app.api.personal_stage:create_app` и healthcheck `/health`. Корневой `railway.toml` запускает Business и рассчитан на другой сервис. Выбранная конфигурация S1 применяет миграцию исключительно через явно заданный DSN стенда, затем выполняет подготовку. При отдельном ручном запуске оператор выполняет следующие команды в окружении тестового сервиса. Первая команда требует DSN выделенной базы во внешнем окружении. Вторая команда идемпотентно создаёт пустую синтетическую привязку и узкое полномочие на единственного контрольного получателя. Конфликт и отзыв сохраняются при повторе. Третья команда запускает HTTPS-бэкенд за прокси площадки.

```sh
DATABASE_URL="$GATE_PERSONAL_STAGE_DATABASE_URL" alembic upgrade head
python -m app.personal_telegram.work_stage provision
uvicorn app.api.personal_stage:create_app --factory --host 0.0.0.0 --port "$PORT" --no-access-log
```

## Проверка в Work

1. Подключить тестовый адрес в приватной установке Work. В новой сессии запросить обновление каталога и, когда потребуется, повторить OAuth-вход. Сохранить ревизию сервера, тип и версию клиента, отметку времени и фактические подтверждения интерфейса.
2. В каталоге сверить шесть команд с префиксом `gate_personal_command_`. Для `readiness`, `status` и `result` требуется `gate:personal:jobs:read`, для `prepare` и `execute` — `gate:personal:send_text`, для `cancel` — `gate:personal:jobs:cancel`. В каталоге стенда дополнительно есть `gate_personal_file_probe`.
3. Вызвать `readiness`. Ожидаются `journal_ready=true` и `runtime_connected=false`. Владелец с правом подготовки получает `test_target` с двумя непрозрачными ссылками. Ссылка на адресата действует до пяти минут и ограничена сроком полномочия.
4. Подготовить синтетический текст с новым `request_key`, прервать получение первого ответа, вернуться и повторить тот же запрос с тем же ключом. При необходимости заново получить ссылку на того же адресата. Ожидаются один `operation_ref` и `replay=true`. Тот же ключ с изменённым текстом даёт конфликт. Если хост не позволил воспроизвести потерю ответа, это фиксируется отдельно от автоматического теста потери ответа.
5. Проверить статус, поставить команду в очередь через `execute`, получить статус `queued`, отменить и получить `cancelled` через `result` после возврата в чат. При запросе той же операции другим клиентом или владельцем доступ отклоняется. В отдельной БД на один уникальный ключ ожидается одна запись операции и ноль записей попыток.
6. Скачать публичный образец с `/s1/fixture.txt`, приложить его к сообщению через штатный выбор файла Work и вызвать `gate_personal_file_probe`. Открыть возвращённую ссылку на устройстве и сверить размер и SHA-256. Лимит равен длине образца. Образец равен строке `Gate MTProto RU S1 file roundtrip` в ASCII с одним завершающим LF. Шлюз сравнивает входные байты и возвращает постоянный публичный файл с этими же байтами. Вложения другого содержания отклоняются. Зафиксировать видимость выбора файла и скачивания в мобильном клиенте. [Дескриптор файла Work](https://developers.openai.com/plugins/reference#file-inputs)
7. Приложить к #696 редактированный результат по каждой проверке. Допустимы SHA, статус, счётчики и контрольная сумма публичного образца. После окна испытаний остановить отдельный сервис и отозвать тестовое OAuth-подключение. Штатная проверка готовности Gate сравнивает Alembic head БД с head своей сборки. Старый процесс Business на общей базе после миграции показал бы расхождение. Выделенная БД даёт проверить S1 независимо. Откат приложения сохраняет журнал. Откат новой миграции удаляет четыре таблицы и применяется только к одноразовой копии.

## Реестр процессов и отправителей

`python scripts/personal_telegram_writer_inventory.py` строит перечень по `app` и `src` со строкой исходника каждого совпадения. В этой ревизии обнаружены 43 места вызова в 31 файле, 12 сборок URL изменяющих методов Bot API в двух файлах и пять конструкторов клиента пользовательской сессии. Записи разных списков могут относиться к одному действию. Результат публикуется как артефакт CI.

| Путь | Отношение к S1 |
| --- | --- |
| `enrollment.py`, `auth_check.py` в `app/personal_telegram` | Исторический вход и проверка локальной авторизации. Отдельные команды оператора. |
| `local_runtime.py`, `private_group.py` | Исторические отправка и создание группы через пользовательскую сессию. |
| `cloud_worker.py` | Клиент MTProto и исполнитель под арендой. Синтетическая привязка отклоняет аренду и замену материала сессии. |
| `app/services/telegram.py`, `app/infrastructure/alpha_owner_test_runtime.py` | Формируют URL Bot API. В каталоге S1 отсутствуют пути Business и Alpha. |
| Business, Alpha, Beta, исторические AQUB и внутренние адаптеры | Исходные места вызова перечислены в JSON. Полнота динамических вызовов и единый контроль фактической отправки относятся к последующим спринтам. |

## Воспроизведение инженерной проверки

`pytest -q tests/test_personal_work_stage.py tests/test_personal_command_grants_postgres.py tests/test_personal_command_runtime_postgres.py` запускается с `DATABASE_URL` и `PERSONAL_COMMAND_TEST_DATABASE_URL` одноразового локального PostgreSQL 17. Первый файл создаёт собственную БД, накатывает прежний head, записывает синтетический проект, применяет миграцию, сверяет старые данные и проверяет HTTP-приложение с подписанными токенами. Индивидуальные тесты различают потерю ответа, новый экземпляр приложения, права доступа, журнал и известные байты файла. Для этой проверки JWKS и входящий файловый хост тестовые. Реальная установка Work и открытие файла на Android фиксируются отдельным результатом.
