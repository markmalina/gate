## Diagnosed archive schema mismatch

Diagnostic PR #687 was deployed as `fc623afdadc6e65192eea76668f05d3fbc56534d`.
Ops deployment run: `AlphaCenter/aqub/actions/runs/35578675054`.
The owner status then showed intake enabled, all required configuration present,
the current webhook received at `2026-09-21T07:39:39Z`, a pending inbox with 819
attempts and `dropbox_call_worker_failed`, and no archive newer than September 18.

PR #686 raised the worker's Dropbox ceiling to 100 MiB on September 18 but did
not migrate `ck_phone_call_recordings_bounded_size`. Migration
`0053_audio_closeout` still capped persisted calls at 25 MiB. The worker accepts
a larger supported file, downloads it, then fails its archive INSERT before
committing the Dropbox page cursor. Every retry reaches the same file; later
small files on the page are starved. The retained source authorized by #685 is
37,585,783 bytes and exercises this mismatch.

Repair execution: `gate-call-schema-repair-20260921T084500Z`. Migration
`0104_dropbox_call_source_limit` changes only the phone-call archive bound to
the already accepted 100 MiB. It preserves Telegram's 25 MiB limit and all
transcription budgets, idempotency and unknown-outcome protections. Downgrade
refuses while larger rows exist; it never deletes recordings. Roll back code
to `fc623afdadc6e65192eea76668f05d3fbc56534d` if readiness regresses; keep the
compatible widened schema when preserving already-ingested larger rows.

The regression executes the actual Alembic upgrade/downgrade against disposable
PostgreSQL tables: reproduce the old failure, accept both source sizes and the
100 MiB boundary, reject invalid sizes, preserve Telegram's boundary, and prove
that downgrade refuses data loss. A local relational check also exercises the
CHECK expression emitted by Alembic.
