# Gate: план улучшений и последовательность спринтов
Дата: 2026-11-02. Статус: ПРЕДЛОЖЕНИЕ, НЕ ЗАПУЩЕНО.
Основание: [завершённое исследование](RESEARCH.md).
Поручение владельца: планирование и сохранение документов; не изменение кода, настроек, issues/PR и не запуск спринтов.
Ни один предлагаемый ниже grant/допуск/срок/порог не считается согласованным публикацией этого плана.

## Цели и граница результата
1. Воспроизводимый путь изменения → установленная версия → проверенный пользовательский результат.
2. Watch: ранняя карточка, полный текст той же записи в той же private Mark issue, автономная обработка, восстановление и координация с Work без повторной STT.
3. Ответы: снимок прочитанного диалога, отказ до provider dispatch при новом durably принятом событии, актуальный контекст и новое согласование.
4. Уменьшение повторной работы без ослабления scope, idempotency, сохранности исходников/журналов и секретов.

Четыре раздельных состояния: SOURCE (код проверен) → CI (проверен exact кандидат) → RELEASE (версия/схема/режим реально установлены) → USER_ACCEPTANCE (в подключённом интерфейсе наблюдался нужный исход).
DONE спринта означает его конкретную ступень; DONE продукта требует USER_ACCEPTANCE. Один статус не подменяет остальные.
Опубликованное поручение reviewer не является accepted/running/terminal review. Ответственность за цепочку сохраняет исполнитель выпуска до фактического принятия передачи.

## Можно ли выпускать части отдельно
Да, в основном через раздельную активацию уже имеющегося кода:
1. Диагностический механизм Ops/client отдельно от Gate app.
2. Установка Watch app/schema0119 с прежним Actions mode и выключенными earlyInbox/Work features.
3. Отдельный ограниченный ввод persistent+earlyInbox.
4. Reply guard после принятого Watch baseline, не ожидая Work STT и всего backlog.
5. Work fallback отдельно после доказательства доступности STT.

Предпочтительно не вырезать ретроспективно Watch0118/0119: общий worker/models/status использует журналы; поддержка receipts/unknown должна сохраняться даже при отключении новых claims. Для физического удаления понадобится новый кандидат и доказательство отсутствия зависимостей; экономия не доказана.
Флаги не отменяют проверку всего установленного source/schema. «Выключено» не значит «можно пропустить upgrade/compatibility tests».
PR747 нельзя просто merge после766: helper жёстко ограничивает0115/его0116. Даже GitHub mergeable=true не проверяет семантику миграций.
Полный общий dispatcher refactor, Work STT и parallel sequences не являются условием первого полезного Watch выпуска, если реальные тесты нужного маршрута проходят.

## Порядок спринтов
S1 рабочий предвыпускной контроль → S2 установленный совместимый Watch baseline → S3 полезный автономный Watch → S4 интегрированный guard-кандидат → S5 установленная и принятая защита → S6 резервный путь Work.
S4 source-подготовка возможна послеS2; его runtime-выпуск сериализован и не пересекается сS3. По умолчанию одна активная release lane, один интегратор. Новые параллельные Work не предлагаются.
S6 зависит отS2–S3 и реальногоSTT, но не должен задерживатьS4–S5.
Каждый спринт заканчивается своим конкретным результатом. Если граница расширяется — зафиксировать незавершённость и новую развилку, не объявлять source milestone всей приёмкой.

## S1 — действующая проверка условий следующего Watch выпуска (подробно)
### Польза и результат
Существующий авторизованный исполнитель действительно наблюдает точный Gate target/pending state и выдаёт проверяемую квитанцию для выпускаS2. Устранён конкретный блокер, при котором нужная проверка отменялась ещё доjobs.
Не считать завершением: merge404, зелёныйCI, подготовленный packet, UNKNOWN/STOP или запрос reviewer.

### Границы
- Ops399/404: принятый queue eligibility successor, его установка/binding.
- Gate736/766: только согласованные диагностические workflow/locks, без изменения app/migrations.
- Узкие нормативные документы из768: definition of done, actual release route, current pointers. В этой части не менять owner powers.
- Использовать существующий fixed-target route; новых providers, credentials, service fleets, общих control frameworks не создавать.
- Новая установка Gate приложения, STT, отправки, БД-миграции и изменение очереди не входят вS1.
- Lease/archive/reviewer records соблюдать при реальном запуске; в плановой работе они не создаются.

### Входы и зависимости
1. Exact heads/currentmain и фактическое состояние существующих reviews, в частности425; принятие source не переносить на изменённый candidate.
2. Existing Gate project/environment credential доступна защищённому executor; значения не читать в чат.
3. Текущий новый bounded owner grant на установку/одну fixed-scope read observation; прежний6562244412 остаётсяSPENT.
4. GitHub contents/workflows/artifact read и ограниченная запись control paths; Ops repository authority на этот scope.
5. До триггера проверить доступность Actions/бюджета, active lease/запуск и разрешённый временной интервал. Billing изменение не входит.

### Последовательность после отдельного старта
A. Зафиксировать один действующий release checklist: exact candidate/target/schema/driver/writer/backup/rollback, источник каждого факта и допустимая свежесть. Удалить только противоречащие текущие указания в нормативном входе, сохранить историю.
B. Повторно использовать404; подтвердить установку exact reviewed executor и совместимость всех5control paths клиента. Source changes only where required for agreed admission/queue routing.
C. Целевые offline негативы: чужие PR/labels/owners, все4purpose routes, старыйgrant, edited/stale request, неверные типы/SHAs, history mismatch; нужный запрос не вытесняется неeligible workflow. Один необходимый CI по final source и фактический terminal независимой проверки.
D. Выполнить один новый разрешённый original. Сохранить настоящийrun/jobs/artifacts/raw digest и независимый verifier result. Целевой результат — OBSERVED с точным target и достоверным pending=0; null не превращать в0.
E. Сопоставить результат с следующим Watch release: нужный installed executor применим к актуальному app/schema0119; actualpending не загрязнён чужими staged changes; следующий конкретный маршрут и его недостающие условия известны. Evidence freshness проверяется снова непосредственно передS2, не объявляется вечной.
F. Действующий ответственный заS2 принимает результат; передача подтверждается фактом принятия/старта, а не только новым issue.

### Критерии завершения и доказательства
- Исправление установлено и диагностический клиент реально исполнился через разрешённый маршрут.
- Original не отменён доjobs; получен валидный observed receipt, распознанный verifier; independent review действительно завершён.
- Подтверждён конкретный infrastructure predicate, блокировавшийS2: fixed target/pending clean. UNKNOWN/STOP означает BLOCKED, а не DONE.
- Присутствует исполнимый следующий Gate-owned release route дляS2; если его нет/он требует ещё неизвестной capability, S1 остаётсяBLOCKED с названием недостающей операции. Одно наблюдение не объявляется доказательством умения сделатьbackup/migrate/deploy.
- В следующем выпуске всё равно необходимы свежие backup, config/credential-scope и runtime checks; они относятся кS2, не подменяются диагностическимreceipt.
- В итоговой записи: sourceSHA, installedexecutorSHA, clientSHA, runURL, artifact/verifier/actualreview, target scope, observation time, next release, остаточные условия.

### При неудаче
- Нетjobs/нетreceipt/UNKNOWN → без повторного provider эффекта; сохранить состояние и один конкретный код/неизвестность.
- Выявлен новый дефект → исправление только в тех же404/766 и exact диагностическом scope. Если требуется новая capability/широкая архитектура, остановить спринт на решении владельца; не строить цепочку новыхframeworks.
- Staged state неzero → не очищать и не применять чужие изменения. Вернуть наблюдение и отдельную развилку.
- Возврат: отключить новый diagnostic entrypoint либо восстановить предыдущий принятый control client; продуктовый Gate не менялся. Spent grants и историю не сбрасывать.
- Предложенное послабление для доказанногоzero-effect retry применяется только после отдельного изменения правил; этот план его не разрешает.

## S3 — автономный Watch и ранняя карточка с полным текстом
**Результат:** новая завершённая запись появляется в private Mark до STT и получает полный текст в той же issue; для обработки не требуется запуск Work вручную.
**Границы:** существующие persistent/early Inbox flags, writer, future-only cutover и журнал766. Новые Work claims остаются выключены. Старые unknown/rejected не переобрабатывать ради теста.
**Зависимости и доступы:** S2; подтверждённый writer с нужными правами в private Mark; допуск к выбранным новым аудио, действующей модели и бюджету STT; разрешение публикации только в private Mark. Недостающие credentials — отдельная ограниченная настройка, без переноса временного токена Actions на сервер.
**Завершение:** Actions и persistent не выполняют обработку одновременно; завершены прежние операции и проверен durable fence. Реально работают нужные HTTP/MCP пути статуса и доступа к оригиналу. Проверена одна короткая запись и серия: предложение — всего три новые записи. Замерены Dropbox-finished→detected→card→fulltext; задержка Watch/телефон/Dropbox учитывается отдельно.
Предлагаемые ориентиры для согласования: карточка не позднее60s после завершённой загрузки в Dropbox; полный текст записи длительностью до2мин — не позднее180s при доступном STT. Три пробы не доказывают p95 или постоянный SLA.
Outage/repeated event/lost ACK проверять на изолированных fixtures без новых платных STT. Один согласованный контролируемый restart доказывает продолжение durable очереди. Синтетический GitHub outage не называть реальным сбоем GitHub.
**Доказательство:** ссылки на три карточки; совпадение source identity, issue, длины и hash полного текста; фактические времена; учёт provider dispatch; подтверждённое восстановление после restart без дублирующей публикации; фактически выполненная независимая проверка.
**Неудача и возврат:** остановить persistent; сохранить оригиналы, карточки и журналы. Actions вернуть только после drain/fence и проверки совместимости. Иначе driver disabled с ясным статусом блокировки. Unknown STT не повторять.
**PR:**766; новые исправления только в существующем Watch scope.

## S4 — интегрировать защиту ответов с установленной Watch-схемой
**Результат:** один воспроизводимый guard-кандидат поверх фактически принятого Watch main с работающим migration/cutover helper. Это SOURCE+CI, ещё не пользовательская приёмка.
**Границы:** PR747 и только необходимые зависимости cutover из758/760/762/771/Ops375. Сохранить Watch API, конфигурацию, режим и прежние миграции. Привязать source/fixture/config к объединённому кандидату. Отдельные parallel-sequence возможности720 не добавлять.
**Зависимости и доступы:** установленный baselineS2; стабильный Watch перед выпуском; фактический результат Delta420 и необходимых последующих проверок; существующий стенд и маршрут cutover. Сначала определить пригодность имеющихся компонентов. Отсутствующая capability — конкретный блокер, а не повод незаметно строить новую платформу.
**Миграции:** добавить новую merge revision с родителями Watch0119 и reply0116; свободный ID выбрать по свежему main. Обновить реальный helper: явно допустимые исходные0115, установленный Watch0119 и конечный joined head; upgrade направлен на joined head. Старые revision IDs и байты не переписывать.
**Завершение:** PostgreSQL upgrade с0115 и установленного0119 до одного joined head; populated journals и unknown сохранены; schema/restore; гонки ingress/send в двух процессах; события обеих сторон, медиа, редактирование и удаление; actual HTTP context_changed с актуальным контекстом; старый клиент без token и legacy send не обходят защиту. Изменённый кандидат проходит свой CI.
**Доказательство:** exact integrated SHA, migration graph, логи PostgreSQL и HTTP тестов, завершённая независимая проверка.
**Неудача и возврат:** кандидат остаётся вне main; работающий Watch не меняется. Production schema не трогать для исправления непринятого кандидата.
**PR:**747 — единственный интегратор. Supporting PR включать только по доказанной зависимости.

## S5 — выпустить и принять защиту ответов
**Результат:** подключённый Work получает snapshot; устаревший ответ реально отклоняется; свежий согласованный ответ доставляется один раз.
**Границы:** точный guarded joined SHA, backup/cutover, подключённый каталог MCP и текущий release pointer.
**Зависимости и доступы:** S4, принятый Watch baseline; согласованное окно недоступности; маршрут наблюдения/остановки старых процессов, backup/restore/config/deploy. Контрольный диалог — только между собственными разрешёнными аккаунтами. Предложение для будущего допуска: не более четырёх исходящих тестовых сообщений, включая документ; точное содержание согласовывается перед тестом.
**Завершение выпуска:** autodeploy действительно выключен до merge; sends off; подтверждена остановка всех прежних ingress/send writers, а не только нулевой счётчик БД; создан backup нужной БД; установлен guarded SHA с joined head и sends off; после проверки включены отправки на том же SHA; повторно подтверждено отсутствие старых процессов.
**Пользовательская приёмка:** чтение контекста → подготовка черновика → новое принятое сообщение → context_changed/sent=false и актуальный контекст без provider send. После нового чтения и согласования — одна отправка. Проверить текст, документ и прекращение оставшейся серии при изменении диалога. Полную матрицу гонок/дублей проверять PostgreSQL и fixtures; live проверка ограничена согласованными сценариями.
Граница гарантии: Gate не отменяет события после последнего допуска отправки и не знает сообщения, ещё не доставленные Telegram в Gate.
**Доказательство:** версия/схема/fleet/flags, реальный каталог подключённого Work, scoped terminal receipts и число попыток, завершённая независимая проверка и видимый результат контрольного диалога.
**Неудача и возврат:** sends off, журналы попыток и unknown сохранить. Старые drafts не отправлять. Предпочтительный возврат — совместимая проверенная guarded версия на joined schema. Возврат к незащищённому binary допускается только с выключенными отправками. Восстановление backup требует оценки записей после backup и допустимой потери данных; не выполнять автоматически.
**PR:**747 и необходимый существующий Ops route; metadata771 не считать всей приёмкой cutover.

## S6 — работающий резерв Work → тот же Watch результат
**Результат:** разрешённый Work получает оригинал, выполняет настоящее STT, сохраняет полный текст в той же issue; Gate принимает его и не запускает дополнительную STT этой записи.
**Границы:** существующий adapter/journal из766, флаги, подключённый каталог и действительно доступный разрешённый STT-путь. Автономный запуск ChatGPT или новый провайдер не подразумеваются.
**Зависимости и доступы:** S3. Сначала доказать доступность скачивания оригинала и реального распознавания в среде Work. Если инструмента нет — представить один конкретный выбор канала/провайдера и допуска владельца; соответствующая часть770 остаётся открытой.
**Завершение:** работают реальные owner claim/start/submit и discovery; выбран новый source, по которому Gate ещё не отправлял STT; совпадают полный текст, hash/length, readback и comment IDs. prepared, saved и accepted различаются. Последующие циклы Gate не создают provider dispatch для принятого результата. Гонки/истечение lease/lost ACK/replay проверяются синтетически на PostgreSQL. Неизвестный исход начатой STT не разрешает повтор.
Порог120s не утверждён: до отдельного решения оставить обращение Work по запросу владельца. Этот этап не задерживает основной Watch и guard.
**Доказательство:** реальная карточка до/после, проверенный оригинал, квитанции распознавания и принятия, отсутствие нового Gate dispatch в проверенном интервале.
**Неудача и возврат:** отключить новые Work claims; сохранить барьеры для уже claimed/started/unknown/prepared/saved/accepted. Обычный Gate обрабатывает только свободные новые записи. Не удалять журнал для разблокировки.
**PR:** повторно использовать766. Если он уже объединён к началу этого этапа, один узкий successor для необходимых изменений, без параллельного продуктового потока.

## Проверки и ограничения
### Необходимые — оставить
- OAuth/owner/scope/private destination/fixed infrastructure target; секреты только в защищённой среде.
- Exact source и проверка кандидата; PostgreSQL для гонок/миграций, восстановление с сохранением данных.
- Оригиналы/receipts/hashes, один принятый результат, sent/failed/unknown, запрет слепого повтора.
- Один driver Watch и последовательные физические выпуски; остановка прежних writers при guard cutover.
- Фактические fingerprint/schema/effective flags и отдельные worker/product наблюдения.
- Реальный HTTP-путь, подключённый MCP-каталог и проверенный пользовательский сценарий.
- Отдельные решения для новых credentials/provider/данных/стоимости/отправок.
- Фактическое завершение обязательной независимой проверки; самопроверка автора её не заменяет.

### Повторы — сократить
- Общий аудит при каждом Work заменить свежей проверкой только изменившихся heads, зависимостей, leases и нужных runtime predicates.
- Не повторять полный CI на неизменённом SHA без нового основания. Docs-only не требуют PostgreSQL/Docker/Windows. Для final runtime candidate сохранить необходимый полный набор.
- Full pytest уже включает часть повторных rehearsals. Оставлять повтор при иной конфигурации/цели, а генерацию используемых evidence не удалять без проверки потребителей.
- Не запускать полный review из-за форматирования квитанции. Изменение runtime/security/executor/source binding требует актуальной проверки.
- Одну неизменяемую квитанцию связывать ссылками, вместо копирования всей истории в несколько bodies.
- Новые fixture/controller создавать только при доказанной непригодности имеющихся.
- Проверки source, installed executor, caller и operation отвечают на разные вопросы: сами эти различия не являются дублями. Можно объединять организационную упаковку, сохраняя проверки границ.

### Изменения полномочий — только после решения владельца
- Разрешить заранее ограниченный повтор наблюдения после доказанного zero-provider/zero-mutation failure. Задать число попыток, срок, цену и exact scope. UNKNOWN и старые spent grants не оживлять.
- Один ограниченный release grant может охватывать заранее описанные технические переходы и безопасный rollback. Новый target/provider/данные/стоимость остаются за его пределами.
- Изменение обязательных Center/Delta этапов или требований к независимости требует отдельного решения. Удаление устаревших инструкций не создаёт новых полномочий.
- Пока изменения правил не приняты, действующие ограничения сохраняются. Числовые бюджеты повторов и расходов в этом плане не согласованы.

## Решения владельца
**Для принятия плана сейчас:**
1. Принять последовательность Watch baseline → основной Watch → guard → Work fallback и поэтапную приёмку полезных частей без ожидания всего770. Это принятие плана, не автоматический запуск.
2. Решить, менять ли порядок технических zero-effect повторов и объединять ли заранее определённые шаги в один bounded grant. Рекомендация: изменить узко, сохранив unknown/scope/privacy.
3. Выбрать для Watch предложенные60s/180s, другие ориентиры либо сначала измерить базовый уровень без SLA.

**Перед зависимыми действиями, когда готов конкретный пакет:**
4. Новый exact S1 grant на установку диагностического исправления и разрешённое наблюдение; старый spent grant не использовать.
5. Для S2/S3/S5 — окно остановки, exact release/rollback/data scope, лимиты стоимости, новых аудио и тестовых отправок. Не просить общий бессрочный доступ.
6. Только если в S6 подтвердится отсутствие STT в Work — выбрать конкретный поддерживаемый путь с согласованными данными, провайдером и бюджетом. Не запрашивать абстрактное разрешение заранее.

Не нужны новые решения для обычных локальных тестов, чтения доступных receipts, имён внутренних файлов или повторного использования существующего кода в принятом scope.
Полное переписывание Gate и общий рефакторинг не предлагаются.
После выдачи плана остановиться. В этой работе спринты не запускаются; активные PR/issues, код и настройки не изменяются.
