# Аудит голосовых записей и состояния Gate

25 октября 2026 года   Срез 19 03 МСК

Автоматическая доставка существует и работает без Work, но её скорость ограничена расписанием GitHub Actions и обработкой одной записи за запуск. На срез аудита из 28 файлов за 25 октября в Dropbox десять доставлены в приватный Inbox mark, восемнадцать ещё ожидают обработки. Во время проверки очередная запись была обработана сама и появилась как issue №90. Рабочий процесс, конфигурация, очереди и развёртывание в рамках аудита не менялись.

## Прямые ответы

Работает ли автоматическая расшифровка. Да. Активен private Mark Actions → Gate → OpenAI → issues mark. Это подтверждают запуски schedule, квитанции processed/delivered и появление №90 во время аудита без ручного запуска. Постоянный worker Voice отключён.

Обработаны ли все записи за 25 октября. Нет. Найдено 28 файлов, 10 полных расшифровок в №81–90. В статусе Gate 18 received/pending. Исторические 18 файлов и №81–88 уже не отражают текущий срез.

Сколько стоит час и месяц. Обычный gpt-4o-mini-transcribe: ориентир 0,003 USD/мин, 0,18 USD/час. При 30/60/120 мин в день за 30 дней: 2,70/5,40/10,80 USD за распознавание. Дополнительно возможны Actions и ресурсы Railway. Общий внутренний speech-бюджет Gate сейчас 3 USD/месяц.

Какая задержка. По десяти готовым файлам Dropbox → Inbox: от 0:58 до 41:34, медиана 14:55. Это не задержка от Stop на часах. Часть файлов до Dropbox доходила существенно позже; точного времени Stop и появления на телефоне нет.

Работает ли вебхук. События приходят: последняя наблюдаемая отметка 18:52:19 МСК. Но /dropbox/calls/webhook меняет состояние обработчика звонков, а Voice сканируется другим cursor по Actions. Вебхук пока не убирает ожидание Voice.

На какой стадии Gate. Рабочая персональная коммуникационная платформа с production приёмом, архивами, черновиками и подтверждаемой отправкой. Автономные агенты, пользовательские Spaces, отдельный transcription API и облачный MTProto имеют разные незавершённые/отключённые стадии. Это не завершённая единая автономная система.

## Где находятся оригиналы и расшифровки

Dropbox сохраняет исходные файлы /Alpha/Voice. Gate отдельно сохраняет байты оригинала, SHA-256, размер, имя, путь, file ID/revision, duration_seconds и временные метки в PostgreSQL watch_voice_notes. В той же записи находятся исходный полный transcript, модель, состояния распознавания/доставки и GitHub receipt. Это не только краткое резюме и не временный файл runner.

Защищённое чтение: watch-voice:<event_id> возвращает receipt и полный текст; watch-voice-file:<event_id> возвращает оригинал с проверкой хеша. Доступ ограничен owner workspace и разрешённым проектом. Оригинал не публикуется в GitHub.

Inbox здесь — issues приватного markmalina/mark. Первая часть полного текста находится в issue, продолжения длинного текста — в комментариях. Текст режется для публикации, а не заменяется кратким пересказом. Доставка во входящие не означает исполнения содержащихся в диктовке задач. Для разбора и действий нужен отдельный запуск владельцем соответствующей работы.

Наблюдаемый статус Voice: 53 исходных записи в этом контуре за всё время, из них 35 transcribed/delivered и 18 received/pending; 465 потреблённых Actions claims. Эти 35 не следует выдавать за число записей только 25 октября.

Отдельно измеряются только подтверждённые временные интервалы. server_modified — серверная отметка версии в Dropbox, а client_modified — переданное клиентом время изменения содержимого. Ни одна из них не доказывает Stop на часах. received_at Gate фиксируется уже после скачивания и ffprobe. Точные STT request_start/request_end и queue claim start в выдаваемой квитанции отсутствуют.

## Пять минут и вебхук

Пять минут заданы в приватном mark: .github/workflows/gate-watch-voice-drain.yml, cron 2-59/5 * * * *. Runner ubuntu-24.04 получает краткоживущий GITHUB_TOKEN с Issues write и OIDC и вызывает POST /internal/watch-voice/drain. Gate проверяет точный private repository, main/run/attempt, hash workflow и .gate/watch-voice-binding.json. Текущий binding enabled=true, scope=future-only.

Именно этот Actions-вызов опрашивает Dropbox files/list_folder/continue для /Alpha/Voice. Он сохраняет весь найденный пакет, но выбирает лишь одну запись и публикует не более одной части текста за запуск. Длинное продолжение тоже ждёт следующий запуск. Процесс STT исполняется в Gate на Railway; runner в основном ждёт HTTP-ответ.

В последних 60 запусках, доступных на первом снимке, интервалы создания runs составили 8:16–30:27, медиана 12:59. Это 59 интервалов примерно за 14 часов 38 минут. Времени постановки каждого cron события в очередь GitHub нет; поэтому интервалы нельзя точно разложить на задержку планировщика и отсутствующие запуски. В двух вечерних jobs от создания run до старта job было 3–4 секунды; основной наблюдаемый разрыв возникает между самими запусками.

Последние продуктивные runs 40208172196 и 40208871540 закончились success с considered=1, published_parts=1, delivered=1. Run40209543299, также schedule, доставил №90 в 19:00:00 во время аудита. Во всех прочитанных продуктивных jobs выполнена реальная обработка; зелёный idle run сам по себе обработки не доказывает.

Dropbox webhook существует и принимает подписанные HMAC события: /dropbox/calls/webhook. Код обновляет только DropboxCallInboxState.pending/webhook_received_at. Voice использует отдельную WatchVoiceCursor; связи webhook → Voice wakeup/Actions dispatch в проверенном коде нет. Последнее событие в live статусе — 18:52:19 МСК, последнее обновление состояния Calls — 18:53:58. Наличие события доказывает приём Dropbox event в этот момент, но не доказывает отдельное событие для каждого файла Voice.

Даже обработчик Calls не делает STT внутри HTTP webhook: он записывает флаг, а фоновый цикл проверяет cursor. В коде цикл спит 30 секунд по умолчанию; фактическое значение переменной в Railway через текущий доступ не прочитано. Флаг pending не является сигналом прерывания sleep. Для Voice постоянный цикл существует, но ordinary_worker_enabled=false; в railway.toml установлен принудительный выключатель Voice worker и включатель OIDC.

## Сравнение вариантов запуска

| Вариант | Задержка после Dropbox | Надёжность и сложность | Дополнительные расходы |
| --- | --- | --- | --- |
| Текущий Actions | Наблюдаемая медиана до Inbox 14:55; пакет растёт по одной записи за run. | Уже работает, краткоживущий writer; зависимость от cron GitHub и его квот. | Короткий job округляется до минуты даже при пустой очереди. |
| Постоянный Voice worker с опросом 30 секунд | Цель: до 30 секунд ожидания свободного цикла плюс download/STT; очередь обрабатывается подряд. При занятом worker задержка больше. | Самый простой следующий выпуск; нужен один активный driver, проверенный writer и сохранение watermark/receipts. Есть кандидат PR766. | Без отдельной VM при использовании существующего Gate; дополнительный CPU/DB/сетевой ресурс измеряется. Actions вне пути доставки. |
| Webhook и постоянный worker плюс резерв | Цель: запуск сканирования в течение нескольких секунд от event; STT остаётся. | Добавить durable pending и wakeup Voice. Webhook повторяется и не содержит готовый файл; cursor всё равно нужен. Резерв нужен при потере event/рестарте. | Похож на постоянный worker, меньше пустых Dropbox polls; небольшая добавочная реализация. |
| Webhook запускает Actions | Пропадает ожидание cron, но остаётся запуск runner и one-note cap. | Нужны полномочия dispatch и переработка exact OIDC/run admission. Для пакетной загрузки требуется отдельная логика. | Запуски на события уменьшают пустые jobs, но сохраняют стоимость и зависимость от GitHub. |

Рекомендация: довести существующий PR766 и перейти на один постоянный worker с опросом 30 секунд, затем измерить эффект. Это даёт основной выигрыш без нового брокера и сервера. Если оставшиеся 0–30 секунд существенны, подключить уже имеющийся webhook к durable Voice pending/wakeup; резервный скан раз в 1–5 минут. Для этого сценария разумный старт резерва — 60 секунд, а увеличение до 5 минут возможно после испытания пропущенных событий. Короткий debounce 1–3 секунды позволит собрать пакет.

Текущий main worker нельзя просто включить переменной: startup её перезаписывает, а будущий режим должен сохранять future-only watermark, исключать два одновременных driver и не позволять одной unknown публикации блокировать всю очередь. PR766 как раз готовит explicit driver mode, но остаётся open/unmerged, не развёрнут и не принят по реальным новым файлам.

## Сколько это стоит

Обычный путь использует gpt-4o-mini-transcribe через https://api.openai.com/v1/audio/transcriptions. Это подтверждено validate_settings, pinned model-access.lock и десятью runtime receipts. gpt-4o-transcribe доступен только для отдельно разрешённых recovery-попыток; он не является автоматической fallback-моделью для каждой записи.

| Модель | Ориентир за минуту | Ориентир за час | Учёт токенов за миллион |
| --- | --- | --- | --- |
| gpt-4o-mini-transcribe | 0,003 USD | 0,18 USD | input 1,25 USD; output 5 USD |
| gpt-4o-transcribe | 0,006 USD | 0,36 USD | input 2,50 USD; output 10 USD |

Официальные поминутные величины — estimated cost. Gate считает microusd по provider-reported input/output tokens и этим ставкам; фактическая минута может отличаться. Формула mini: (1,25 × input_tokens + 5 × output_tokens) / 1 000 000 USD, с округлением вверх до micro-USD. Платёж за пополнение API и внутреннее начисление за распознавание — разные показатели.

| Запись в день | Минут за 30 дней | mini обычный путь | 4o если весь объём на нём |
| --- | --- | --- | --- |
| 30 минут | 900 | 2,70 USD | 5,40 USD |
| 60 минут | 1 800 | 5,40 USD | 10,80 USD |
| 120 минут | 3 600 | 10,80 USD | 21,60 USD |

Фактическая сумма за 25 октября отдельно не установлена. Защищённые Watch receipts не выдают duration/token usage/settlement, а доступного разрешённого запроса к ledger по дате и event ID нет. По числу файлов, размеру M4A или длине текста нельзя достоверно восстановить минуты и списание. Для точной суммы нужен read-only join watch_voice_notes → reservation keys watch-voice:<id> → settled usage с длительностью/моделью и периодом, затем сверка с OpenAI Usage/Costs. Нельзя приписывать сегодняшнему дню общий месячный счётчик.

Текущий внутренний speech ledger за октябрь: потолок 3,000000 USD; settled 0,709851 USD; reserved 0,166800 USD; remaining 2,123349 USD; 149 settled операций и одна unknown. Это учёт Gate для общего контура Telegram/Calls/Watch, а не банковская выписка OpenAI и не баланс API. По сравнению с первым снимком за время аудита settled вырос на 0,006427 USD и count на один; attribution именно этому файлу без join не считается доказанной.

Ориентир 60 и 120 минут ежедневно превышает текущий потолок 3 USD даже без звонков и Telegram. При mini 3 USD соответствуют примерно 1 000 минутам в месяц до иных расходов; 30 минут ежедневно оставляют лишь около 0,30 USD на прочее. До отдельного решения лимит автоматически не увеличивается. На один запрос резервируется запас, по умолчанию 100 micro-USD за секунду и минимум 5 000 за часть; это резерв, а не тариф или минимальное списание.

Дополнительного LLM пересказа в цепочке Watch → issue нет: текст передаётся полным, форматирование и деление на комментарии локальные. В Calls/Telegram summaries строятся extractive-ru-v1 обычным Python без отдельного provider запроса. Предыдущие 1 000 символов части могут передаваться как continuity prompt следующей части и входят в token usage. Анализ в Work или отдельными агентами относится к другим задачам и бюджетам. Автоматических повторов STT нет; отдельно разрешённые recovery оплачиваются дополнительно, а unknown могут удерживать резерв.

## Насколько быстро можно получать текст

При текущем сценарии и пустой очереди минимум уже наблюдался: 58 секунд от Dropbox до Inbox. Типичный наблюдаемый результат десяти готовых файлов — около 15 минут, максимум 41:34; текущая очередь делает прогноз следующего файла хуже. От Stop на часах SLA установить невозможно: нужны замеры Samsung и Dropsync при заблокированном экране, экономии энергии и восстановлении сети.

После постоянного worker разумная цель для короткой записи — десятки секунд после попадания в Dropbox, ориентировочно 10–60 секунд при свободном worker и обычной сети. Это инженерная цель, не измеренный сейчас результат и не гарантия для часовых записей. Готовый текст может появляться через 15–90 секунд от Stop только если передача с часов и загрузка телефона сами укладываются в несколько десятков секунд. Полностью нулевой задержки у передачи и STT нет.

Расшифровка прямо во время диктовки требует доступа к живому микрофонному потоку: приложение на часах/телефоне передаёт PCM по WebSocket либо WebRTC, сервер получает частичные события, сохраняет финальные сегменты и после окончания публикует один окончательный результат. Нужны обработка обрыва сети, локальный буфер, порядок сегментов, управление ключом на сервере и измерение батареи часов.

Штатная используемая связка Samsung Recorder → готовый файл → Dropsync → Dropbox не предоставляет Gate поток микрофона. Dropbox webhook сообщает об изменении файлов, он не открывает живую запись. Для realtime потребуется другой источник потока/собственное приложение; одной настройкой вебхука это не решается. Официальная актуальная realtime transcription документация рекомендует gpt-live-transcribe, тариф 0,017 USD/мин, около 1,02 USD/час. Этот путь в текущей Gate policy не разрешён и здесь не запускался.

### Незавершённость и устаревшие документы

Подтверждённые source-проблемы: два POST /mcp собираются через разные роутеры, и первый dispatcher обходит дополнительные transcription tools; отдельный alpha_transcriptions путь не применяет speech budget reserve перед provider I/O; его restart reconciliation отмечает все running parts interrupted без привязки к живому lease. Это выводы по коду, не наблюдавшиеся в этом аудите новые production инциденты и не доказательство перерасхода.

Также /ready и ops worker registry не дают полного контроля всех фоновых задач; для Watch нет полного списка очереди/перезаписей и дневной стоимости. Вновь найденную очередь из 18 файлов невозможно честно разложить на индивидуальные состояния через нынешний публичный интерфейс. Архивирование Voice в DB есть, но доказанная общая политика срока хранения, purge и backup/restore для этого класса данных не установлена. Миграции конкурирующих feature PR нужно сводить перед выпуском, а не сливать их пакетом вслепую.

## Приоритетный план изменений

Все пункты ниже — предложения. Никакие функции, бюджет, расписание, source binding или production-переменные этим отчётом не изменены. Оценка труда — предварительная инженерная оценка; денежная стоимость разработки зависит от исполнителя.

### 1 Завершить прозрачную диагностику Voice

Добавить read-only inventory по дате с file ID/rev, event ID, duration, текущими фазами, last_error, queue age и ledger attribution. Сохранять обнаружение, claim, normalize, provider start/end и outbox timestamps; без текста и секретов в операционных логах.

Эффект: каждый из 28 файлов имеет объяснимый статус, сутки имеют проверяемую стоимость; доступно точное разложение задержки.

Труд 0,5–1,5 дня. Новая подписка не нужна; малый объём метаданных в DB.

Проверка: Сверка Dropbox↔Gate↔issue 100%; сумма дневных ledger entries воспроизводится; тест пропавшего файла/ошибки показывает конкретную причину.

### 2 Выпустить один постоянный driver по существующему PR766

Завершить writer/private-target preflight, startup/migration evidence и безопасный выбор режима. Отключить старый Actions driver при cutover; сохранить originals/cursors/watermark/claims. Начать с 30-секундного polling, не переносить обработку в Work.

Эффект: убрать межзапусковые ожидания 8–30 минут и one-note-per-run; обработать пакет последовательно. Цель пустой очереди: P95 Dropbox→claim ≤35 секунд при свободном worker.

Оценка 1–3 инженерных дня после доступа к текущему Ops контракту; отдельный сервер не предполагается. Экономия Actions до расчётных 18–51,84 USD gross/месяц при указанных сценариях; фактическая экономия зависит от квот.

Проверка: Новая запись, пакет из 20, обрыв сети, restart, replay и 24 часа наблюдения. Ровно один driver; по одному issue на source revision; старые watermark и journals сохраняются; rollback приложения без downgrade данных.

### 3 Подключить webhook к Voice после измерения polling

HMAC handler быстро фиксирует durable Voice pending и будит существующий worker. STT выполняется после ответа webhook. Резервный cursor scan раз в 60 секунд; затем 1–5 минут по результатам испытаний.

Эффект: сократить оставшиеся 0–30 секунд обнаружения, уменьшить пустые Dropbox запросы. Основную задержку Actions уже убирает пункт 2.

Ещё 0,5–1,5 дня, без нового брокера/VM в простом варианте; малые ресурсы Gate.

Проверка: Событие→claim P95 ≤5 секунд при свободном worker; дубли webhook не дают дубля STT/issue; пропущенное событие восстановлено резервом в пределах выбранного интервала.

### 4 Уточнить бюджет и устранить исторические unknown

Сначала отчёт по дневным списаниям и provider balance; затем отдельно согласовать требуемый speech ceiling под 30/60/120 минут плюс звонки. Unknown не повторять, проверить provider/result/ledger без новой оплаты.

Эффект: нет внезапной остановки при 60–120 мин/день и нет повторного счёта за тот же uncertain effect.

Труд 0,5–1 день. Ориентир STT 2,70/5,40/10,80 USD в месяц; это расход, а не требуемая сумма пополнения.

Проверка: Порог бюджета блокирует запрос до I/O; usage/settlement сверяются; восстановление неизвестной доставки не вызывает повторного provider request.

### 5 Измерить часы телефон и Dropsync

На имеющемся устройстве записать Stop, появление файла на телефоне, начало/конец Dropbox upload. Проверить заблокированный экран, разрешённую фоновую работу, батарею и поезд без сети.

Эффект: доказать и уменьшить задержку до сервера, которую Gate не контролирует.

20–40 минут участия владельца плюс анализ журналов; новая подписка не предполагается.

Проверка: Пять коротких проб онлайн и одна offline→online, повтор на следующий день. Замер реального Stop, без подстановки имени файла.

### 6 Закрыть незавершённые пользовательские функции отдельно

Продолжать #722/#745 и #696/#742 только по их приоритету; синхронизировать README, parent pointers и статусы. Общий transcription dispatcher/budget/lease debt исправлять до расширения Alfa jobs.

Эффект: новые входящие не приводят к устаревшей отправке; доступные команды совпадают с каталогом; фоновые задачи видны.

Отдельные bounded задачи, ориентир 2–5 дней на первую наиболее важную функцию; стоимость не включать в цену часа аудио.

Проверка: ASGI tests реального /mcp, race test inbound-stop, два worker с lease, negative budget test; затем соответствующая ограниченная пользовательская приёмка.

### 7 Подготовить смену модели до отключения

Официальная deprecation page указывает отключение gpt-4o transcription семейства 26 февраля 2027. Отдельно испытать актуальную замену gpt-transcribe на небольшом согласованном наборе; обновить pinned policy, cost accounting и лимиты.

Эффект: отсутствие планового прекращения STT в феврале. Это не причина сегодняшней очереди.

Ориентир 1–2 дня на совместимость и сравнение; актуальная замена по официальной таблице 0,0045 USD/мин, 0,27 USD/час. Менять сейчас автоматически не нужно.

Проверка: Точность русской речи, пунктуация, имена, длинные части, usage accounting и latency на одинаковых аудио; выпуск отдельно после оценки качества.

## Что осталось недоступным

Для полностью замкнутого аудита нужны: журналы часов/Samsung/Dropsync; безопасный список всех watch_voice_notes по дате с duration и фазами; связанные speech ledger entries/usage; свежие Railway deploy/build/startup/worker logs и resource bill; текущий GitHub plan/quota/budget; OpenAI Usage/Costs и credit balance. Отсутствие этих источников указано в соответствующих выводах и не заменено предположениями. Существующие ограничения доступа не обходились через provider UI и секреты не извлекались.

Минимальный следующий результат — сверяемый дневной inventory и выпуск уже подготовленного постоянного worker. Это даёт измеримый эффект в ежедневной работе. Потоковую диктовку стоит рассматривать отдельным продуктовым этапом после устранения текущей очереди.
