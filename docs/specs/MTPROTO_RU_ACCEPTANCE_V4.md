# Программа приёмки. Gate MTProto RU v4.0

Приложение к [техническому заданию](MTPROTO_RU_SPEC_V4.md) и [инженерному контракту](MTPROTO_RU_ENGINEERING_V4.md). 62 пронумерованные проверки — план испытаний будущей реализации. Номера T01–T38 сохраняют смысл из редакции v3. T39–T62 уточняют новые пилоты, отдельные продуктовые операции и эксплуатацию.

## 1. Среды, данные и протокол

- **Модуль** — детерминированные тесты политики, состояния, схем и Telegram-ответов на синтетических объектах.
- **БД** — существующий HTTP/MCP-путь Gate, проверяемый OAuth-клиент, временный PostgreSQL 17 с транзакциями, конкурентными вызовами, применёнными миграциями и перезапуском. SQLite и имитация блокировок недостаточны для проверки гонок.
- **Стенд** — собранный образ, отдельные API/worker-процессы, отдельное хранилище, управляемые прерывания, возможность ограничивать подключения и внешние действия. Восстановление резервных копий проверяется здесь.
- **Work** — реальный подключённый клиент Марка и новая сессия с Gate M. Для входа, первого сообщения, группы, бота и скачивания файлов обязательна проверка основного мобильного сценария Android. Состояние настольного клиента фиксируется отдельно при его использовании.
- **Telegram** — ограниченный живой сценарий на подтверждённом личном RU. Нужны контролируемые группа с темами и тестовыми сообщениями, аккаунт с известными правами, бот с заранее известным поведением и при необходимости тестовые объекты администратора. У каждого изменения названы цель, окно, число эффектов и разрешённая очистка. Для тестов изоляции второго аккаунта используются фикстуры.

Проверяющий фиксирует версию источника, дату и среду, начальное состояние, действие, ожидаемый и фактический итог, обезличенное доказательство и отклонения. В личном Work доступны разрешённые ID и ссылки. В публичном репозитории достаточно результата, чисел и непрозрачной квитанции. Итоги выполнения тестов имеют статусы «прошёл», «не прошёл», «заблокирован», «не запускался». «Корректный отказ» является успешным тестом только там, где ожидаемым результатом прямо указан отказ.

Для каждой обязательной операции из C01–C24 разработчик ведёт строку с видом peer, правом, версией, средой, тестом и результатом. Если тест ниже содержит несколько глаголов, каждому нужен свой пример и квитанция либо ожидаемый запрет в соответствующей среде.

## 5. Доказательства и завершение

Для значимой проверки фиксируются: ID требования и теста, исходная/установленная ревизии, версия контракта и среды, время, объём полномочия, ожидаемая и фактическая цель, число операций/попыток/внешних эффектов, ID или обезличенная квитанция, исход и незакрытая причина. Для групп в приватном отчёте проверяются автор и тема, для ботов — версия клавиатуры, признак результата и причина остановки. Для файлов — байты или наблюдаемые медиа-атрибуты соответствующего типа.

Для live-доказательства явным образом записать, какой результат независимо виден владельцу в Telegram или Work. Успешный технический ответ о принятии запроса в очередь сам по себе не подтверждает отправку. Отдельно перечислить локальные, стендовые, установленные и пользовательские результаты. В отчёте по полному объёму привести покрытие глаголов, а также знаменатель, прошедшие, неуспешные, заблокированные и не запущенные проверки. Каждый незакрытый обязательный случай сохраняет свой статус до устранения или согласованного пересмотра объёма.

Приёмку очередного спринта закрывает демонстрация из раздела 5 [основного ТЗ](MTPROTO_RU_SPEC_V4.md). Полную приёмку закрывает решение Марка по всем обязательным функциям и известным остаточным ограничениям.
