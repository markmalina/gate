## 1. Цель и граница

Одна команда `gate_queue_approved_reply_sequence` должна принимать от 2 до 50 уникальных, заранее сохранённых текстовых черновиков одного адресата, reply task, разговора, проекта и RU/BY-аккаунта. Марк подтверждает всю финальную упорядоченную серию одним действием.

Нужно изменить контракт целиком, а не только число в одном месте: входную схему, прикладную проверку, защиту persistence-слоя, выходную схему, описание инструмента и актуальную документацию.

В эту работу НЕ входят:

- параллельные сетевые отправки и новый планировщик — #716;
- выбор произвольного интервала, случайные паузы, 90/120 секунд;
- массовая рассылка нескольким людям, серии документов или автоделение текста;
- новые MCP-инструменты, поля API, настройки среды или таблицы;
- обход окна Telegram Business, автоматический переход на другой транспорт;
- включение worker, изменение Production-настроек, реальные отправки;
- переработка истории очереди, очистка базы, общий рефакторинг sender.

**Результат стадии проектирования:** этот документ в GitHub и указатель из #715; далее ожидание команды Марка.  
**Результат будущей реализации:** проверенный repository-кандидат с лимитом 50 и доказательствами по разделу 8. Это отдельно от развёртывания и подтверждения работы в Production.

## 3. Обязательный контракт

### 3.1 Вход

| Поле | Требование |
| --- | --- |
| draft_ids | Массив 2–50 валидных UUID, без повторов; порядок значим |
| confirmed | Только true; подтверждение относится ко всему показанному списку в его порядке |
| expected_account | RU или BY; существующую нормализацию application сохранить |
| expected_recipient_chat_id | Непустой адресат; точное совпадение с подтверждённым контекстом |
| interval_seconds | Ровно 60, как сейчас; значение 59, 61, 120 и boolean недопустимо |

Сначала сохраняются все черновики, затем Марку показываются аккаунт, адресат и все финальные тексты с порядком. Только после его подтверждения выполняется постановка в очередь. Увеличение лимита не даёт новой авторизации на сообщения.

Не вводить усечение 51 до 50, сортировку UUID, удаление дублей, автоматическое разбиение на несколько серий или частичный успех.

### 3.2 Привязка и область доступа

Сохранить проверку `gate:messages:send` и explicit access scope.

Каждый элемент должен входить в разрешённые account/project grants и иметь один и тот же кортеж:

`reply_task_id, conversation_id, account_id, project_id, trigger_message_id`.

Проверяются все элементы, включая последний. Смешение даже одного черновика должно отменять всю постановку. Несовпадение подтверждённого аккаунта или адресата не исправляется автоматически.

Сохранить отказы для закрытой задачи/черновика, существующей попытки доставки, уже поставленного в серию черновика, нового входящего reply task и документа в текстовой серии.

### 3.3 Выход и запись

- Возвращаются все N элементов, N в диапазоне 2–50.
- Позиции равны 0..N-1; draft_id на позиции i точно равен входному draft_ids[i].
- Один sequence_id, один task_id/account_id/project_id для всей серии.
- `queued=true`, `sent=false`: принятие очереди не означает доставку.
- `scheduled_at[i] = queued_at + i × 60 секунд`, UTC с timezone.
- В JSON каждого черновика сохраняются существующие ключи, включая `size=N`, `position=i`, scope и подтверждённый аккаунт/адресат.
- Вся серия и одна существующая audit-запись фиксируются одной транзакцией.
- Любой отказ — без частичных metadata/audit/SendAttempt; rollback остаётся обязанностью вызывающего transaction boundary.
- DB schema и Alembic не меняются: 50 помещается в существующий JSON-формат.

### 3.4 Доставка и остановка

Для i>0 отправка допустима не раньше:

`max(scheduled_at[i], SendAttempt[i-1].finished_at + 60 секунд)`.

После задержки нельзя «догонять» расписание пачкой. Последний элемент серии 50 имеет начальный due-time через 49 минут после постановки; фактическая доставка может быть позднее. Это не SLA.

`sent` здесь означает подтверждённый успешный исход транспорта, а не прочтение человеком.

Новая входящая задача в том же контексте, отказ sender, failed или unknown останавливают остаток соответствующей серии. Reserved/sending/unknown без подтверждённого sent не позволяют перейти к следующей позиции. Не повторять неизвестную отправку и не обходить её другим аккаунтом или транспортом.

После рестарта использовать сохранённые metadata и SendAttempt. Повторная постановка тех же черновиков остаётся отклонением `sequence_already_queued`, а не новой идемпотентной API-возможностью. На уровне доставки остаётся существующая защита повторной попытки по draft_id. Не обещать exactly-once внешнего Telegram-эффекта.

## 4. Проект изменения

### 4.1 Единственный источник границ

Оставить константы в `app/application/reply_sequences.py`:

- MIN_SEQUENCE_DRAFTS = 2;
- MAX_SEQUENCE_DRAFTS = 50;
- SEQUENCE_INTERVAL_SECONDS = 60.

Выделить чистую функцию `validate_sequence_draft_ids`, которая проверяет длину и уникальность и поднимает существующий `ReplySequenceError(code="invalid_sequence")`. Текст ошибки размера формируется из констант.

Application вызывает её на прежнем месте, после scope и confirmed. SQL writer вызывает ту же функцию в самом начале, до запроса и индексирования ordered[0]. Это закрывает прямой внутренний вызов writer с 0/1/51 элементом; writer остаётся persistence-адаптером, а не новым публичным auth boundary.

Не переносить остальные проверки и не менять приоритет ошибок application. Для валидного по другим полям списка из 51 элемента — `invalid_sequence` до writer. Невалидный тип/UUID на MCP по-прежнему даёт `invalid_arguments`.

### 4.2 MCP и документация

В descriptor inputSchema и SEQUENCE_SUCCESS_SCHEMA импортировать MIN/MAX из application. Направление зависимостей допустимо: API уже использует application, application не импортирует API.

Описание инструмента формировать с числовыми границами из констант: «Queue 2 to 50 saved drafts…». Сохранить текст про одно подтверждение, порядок и паузы. Схемы остаются закрытыми; не менять названия/required поля/output status/security scope/tool annotations.

В README обновить строку таблицы инструмента и абзац approved message chain: 2–50, уникальность, один адресат/задача, ровно 60 секунд, остановка и `queued != sent`. В PROJECT_HANDOFF добавить актуальную заметку со ссылкой на #715 и этот документ; исторические отчёты не переписывать как текущую истину.

Поиск по всему checkout: `MAX_SEQUENCE_DRAFTS`, `gate_queue_approved_reply_sequence`, `SEQUENCE_SUCCESS_SCHEMA`, «two to twenty», связанный `maxItems: 20`. Менять только ограничения reply sequences, не чужие лимиты 20.

## 5. Известные риски и принятое решение

| Риск | Обработка |
| --- | --- |
| Output schema остаётся 20 | Обязательный контрактный тест результата из 50 |
| Прямой вызов SQL writer обходит application | Общий guard до первого SQL + тесты 0/1/51/дубли |
| DB выдаёт строки в другом порядке | Явный входной порядок; тест с переставленными UUID/created_at |
| Один плохой элемент среди 50 | Негативные тесты с плохим последним элементом; никакой частичной записи |
| Сбой commit / потеря ответа после commit | Rollback до commit; после commit повтор не создаёт вторую серию |
| За 49+ минут появляется входящее сообщение или закрывается окно Business | Повторная проверка sender; остановка, без обхода и слепого resend |
| Worker выключен | Постановка не равна доставке; настройки не менять |
| Реальный Telegram outcome unknown | Терминальная блокировка продолжения, без автоповтора |
| Лимит discovery 500 строк | Существующий отдельный дефект/ограничение, см. ниже |

**Существующий предел discovery.** Worker выбирает первые 500 строк с metadata серии, включая исторические, по created_at/id, затем группирует их. Это не ограничение одной серии 20, но способно скрыть новые серии или загрузить неполную серию. Увеличение числа до 500/1250 не является надёжным исправлением.

Решение #715: не выдавать изменение per-series limit за исправление планировщика и не делать непроверенный рефакторинг worker. Repository-приёмка #715 доказывает новый контракт и полный цикл 50 в контролируемом полном наборе данных. Масштабная эксплуатационная готовность при насыщенном discovery не заявляется. Перед будущим live acceptance потребуется отдельное исправление/доказательство полного discovery серий; адресат архитектурной зависимости — работа над scheduler/#716, но само наличие ссылки не означает её принятие. Никаких Production-запросов для оценки этого риска на стадии ТЗ.

Если основной тест серии 50 или обязательная остановка не проходит даже в полном контролируемом наборе — это блокер приёмки #715, а не разрешённое исключение.

## 9. Совместимость и откат

- Существующие серии 2–20 и их metadata остаются читаемыми.
- Новые серии 21–50 используют тот же формат; миграция и backfill не требуются.
- Уменьшение приёмного лимита при будущем revert запрещает новые длинные серии, но не отменяет уже принятые metadata.
- Старый worker не содержит per-series cap 20; это статическое наблюдение, а не доказательство безрискового production rollback. Discovery-ограничение сохраняется.
- Нельзя удалять/requeue неизвестные попытки ради отката. Управление уже принятыми очередями и production revision требует отдельного точного эксплуатационного действия.
- На стадии ТЗ откат кода не нужен: runtime-код не изменяется.
