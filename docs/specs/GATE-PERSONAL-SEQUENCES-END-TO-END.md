# Личный Gate Марка: полное ТЗ выпуска серий сообщений

**Версия:** 2, 28.09.2026. **Автор проектирования:** α Ops по поручению Марка.
**Основная задача:** [Ops #336](https://github.com/AlphaCenter/ops/issues/336).
**Объём:** довести требования Gate #715 / #716 / #718 до проверяемого личного использования, включая разработку, инфраструктуру, переход и эксплуатацию.
**Статус документа:** переработанное ТЗ для выполнения и приёмки. Это документирование будущей работы; запуск Production и отправка сообщений данным документом не разрешаются.

Этот документ заменяет прежнее неполное описание порядка выпуска в Ops #336. Продуктовые требования #715/#716/#718 сохраняются. Противоречащие ему этапы старых runbook должны быть исправлены пакетом G1 до выпуска. Факты о текущем коде отделены ниже от требуемых доработок.

## 1. Результат для Марка

Марк пользуется личным Gate из подключённого ChatGPT Work:

1. Выбирает свой RU или BY аккаунт и личный Telegram Business диалог.
2. Видит и одним действием подтверждает всю упорядоченную серию из **2–50 отдельных текстовых сообщений** одному адресату и по одной задаче. Подтверждение включает аккаунт, адресата и точные тексты.
3. Gate отправляет первое сообщение, когда разрешён допуск. Следующее начинается **не раньше 60 секунд после подтверждённого завершения предыдущей отправки**. Задержка не вызывает догоняющую пачку.
4. Одновременно работают независимые серии другим адресатам. Медленный диалог не блокирует весь Gate; действуют общие ограничения аккаунта, бота и всех процессов.
5. Любое новое входящее от этого адресата в этом аккаунте — текст, голос, вложение, короткий ответ — останавливает неотправленный остаток. Для остановки не нужны распознавание голоса, классификация и вызов модели.
6. Марк получает в своём проверенном канале Gate-бота уведомление: аккаунт, адресат, сколько отправлено, сколько остановлено, причина, отсутствие автоматического продолжения. Техническое уведомление собеседнику не отправляется.
7. Марк может запросить состояние серии и все сохранённые оставшиеся тексты. Для повторной отправки нужно новое подтверждение: два и более сообщений — новая серия; одно — обычная одиночная отправка.
8. После сбоя Gate честно показывает неизвестный исход и не отправляет сообщение повторно автоматически. Остановленные старые серии не оживают при рестарте.
9. Система работает постоянно: Марку не требуется раз в час продлевать технический допуск или разбираться с базой данных.

**Точная граница остановки:** после зафиксированной остановки Gate не начинает следующий запрос отправки этой серии. Запрос, уже начатый до остановки, может завершиться позже. В интерфейсе он остаётся `sending` либо получает фактический `sent/failed/unknown`; обещать его отмену у Telegram нельзя.

**Вне этого выпуска:** группы, MTProto, документы как элементы серии, автоматическое продолжение после ответа, изменение текстов после подтверждения без нового согласования, отдельная пользовательская кнопка остановки одной серии, перенос всех ресурсов между проектами, продуктовые функции AQUB и Oko. Общая аварийная остановка отправки через Ops входит в выпуск.

Здесь нет дополнительного человека «владелец GateDB». **GateDB означает фактическую базу, к которой подключён Gate.** Найти и проверить её обязан Ops. `reply_sequence_owner_subject` в коде — идентификатор учётной записи Марка, подтвердившей серию. Это не организационная роль. β Gate реализует проверку этой привязки, Ops обеспечивает её корректную настройку существующим разрешённым механизмом.

«Защищённая строка подключения» означает секретный параметр доступа к БД. Марк не должен искать или переносить его вручную. Он используется внутри разрешённого исполнителя; в GitHub и чат попадает только результат проверки без пароля и DSN.

Внутренние помощники автора этого исследования не являются δ Gate. Общий GitHub login тоже не доказывает независимость проверки: нужен отдельный принятый проверяющим пакет и его доказательства.

### Почему встречается AQUB и почему Oko здесь не участвует

Сейчас workflow публикации Gate исторически хранится в `AlphaCenter/aqub`, использует там защищённое окружение и control issue #72. Он умеет публиковать отдельный Gate service. Это техническое место размещения пульта; выпуск приложения AQUB для личных серий Gate не требуется.

Oko — другой проект. В инфраструктурном manifest его сервис указан среди соседей, которых нельзя менять. Доказательств зависимости личных серий Gate от Oko нет. **Заданий Oko в этом ТЗ нет.**

Для данного выпуска выбирается минимальная граница: продукт и приёмка — Gate; исполнитель — Ops; существующий AQUB workflow временно остаётся техническим backend. В новом контракте обязательны отдельные поля `productRepository=AlphaCenter/gate` и `executionHostRepository=AlphaCenter/aqub`, точный Gate service/workspace и отдельные Gate-предикаты. Проверка готовности AQUB-продукта не является проверкой готовности Gate.

Новый логический target `gate-personal-production` — **требуемое, ещё не выпущенное** имя Gate-контракта. Ops связывает его с проверенными ресурсами и текущим backend отдельным reviewed изменением; до этого имя не является рабочей командой. Старое имя `aqub-c1c-production` не следует выдавать за владельца Gate. Физический перенос workflow/секретов в Gate можно выполнить отдельно; он не нужен для выпуска серий. Два одновременно действующих независимых пульта запрещены: нужен общий lock на фактические ресурсы, в том числе для старого fast-deploy.

## 5. Архитектура управления и способ исполнения

### 5.1. Выбранный основной путь

**Существующий защищённый project workflow → закреплённый Ops runner → точный reviewed код/образ Gate → фиксированная команда → проверенный TCP/TLS transport фактической Gate DB.**

Это требуемая реализация. В Ops #337 такого исполнителя ещё нет.

Первый ограниченный технический пакет O1/G1 устанавливает возможность этого пути. Успех означает одновременно: найден фактический endpoint БД Gate, разрешены нужные подключения, удостоверена TLS-идентичность, живой сеанс подтверждает ту же БД и schema, доступны только необходимые права, проверена session-семантика. Одного открытого порта или правильного пароля недостаточно.

Executor:

- до доступа к Production secrets готовит точный образ/исходники и закреплённые зависимости; никаких package-install hooks с выданными секретами;
- получает только минимальную конфигурацию; control-процессу не выдаются Telegram/model credentials;
- запускает allowlisted argv без shell, произвольного SQL, module path и параметра «command»;
- сверяет live flags с ожидаемыми, а не подставляет локально `true` для обхода проверок;
- проверяет целевой workspace, роль, schema и release contract;
- выполняет fixed Gate application operation, затем независимо читает postcondition;
- публикует только очищенную квитанцию, не stdout/raw provider errors и не DSN.

`railway run` не является удалённым исполнением — команда работает локально с переменными сервиса. SSH требует отдельной identity; её готовность и право project token не установлены. Поэтому эти команды не считаются запасным пультом данного выпуска.

### 5.2. Единственная предусмотренная альтернативная ветка

Если O1 доказывает, что существующий TCP transport нельзя безопасно использовать, **не открывать БД наружу и не расширять токен автоматически**. β Gate реализует небольшой authenticated operations endpoint внутри Gate, использующий то же application API и private DB connection. Ops вызывает его из того же защищённого workflow.

Endpoint принимает только enum операций, exact workspace/release, operation ID, intent digest, nonce и TTL; ограничивает размер, частоту и время. Отдельная service identity имеет только эти операции. Обычная сессия пользователя и секрет Telegram не являются авторизацией Ops. Секрет создаётся/передаётся штатным secret-механизмом, не через чат.

**Bootstrap этой ветки:** отдельный reviewed patch на baseline со schema 0111, без миграции 0112 и без новых product flags. Он даёт read-only identity/status и исполнимый baseline freeze/drain. Его preDeploy должен оставаться no-op по schema; проверяется полный migration graph. Новый код возвратим к baseline при отсутствии DB-изменений. Команды для canonical tables до появления 0112 отвечают `unsupported_schema`, не создают их скрыто. Запись durable operation journal новой схемы допускается только после backup и отдельной миграционной границы.

**Для обоих transport freeze обязан работать до 0112:** β Gate/Ops подтверждают поддерживаемый legacy worker flag с restart либо фиксированную baseline-compatible операцию, закрывающую все legacy sequence admission/send entrypoints. Проверяются все процессы и durable attempts, а также запрет повторного включения старого worker другим deploy. Read-only status и переданный `--legacy-workers-drained` не выполняют эту остановку.

Так устраняется цикл «для проверки перед миграцией сначала надо выполнить эту миграцию». Если и bootstrap требует изменения схемы, такое изменение сначала получает собственные backup и reviewed migration evidence; его нельзя спрятать в read-only этап.

После O1 в release record фиксируется **ровно один** transport и его проверенный contract. Ветви не реализуются обе «на всякий случай». Выбор по техническому результату делает Ops совместно с α Gate; Марк не выбирает DSN или способ соединения.

### 5.3. Доказательство фактической базы и состава runtime

Ops собирает три связанных доказательства:

1. **Provider:** project/environment/Gate service, deployment/source SHA, переменные и их reference-связи, routes, mounts, autoscale/replicas, pending changes/auto-deploy.
2. **Runtime:** exact source/deployment, boot/process IDs и config fingerprint всех ожидаемых web/worker процессов; какая конфигурация реально загружена. `/ready` остаётся health-проверкой и не подменяет этот набор.
3. **DB session:** внутри этого runtime и control/migration executor выполняется фиксированная read-only identity/schema-проверка; сравниваются provider binding, database identity, schema ledger и права. Разные DB roles и private/public адреса допустимы при доказанно одной БД. Сравнение паролей не критерий идентичности.

Формат identity proof должен связать server/cluster identity, database identity, schema и origin доказательства; если права не позволяют получить один из маркеров, используется явно утверждённое эквивалентное доказательство, а не `current_database()` в одиночку. В публичный receipt выходят непрозрачная ссылка/безопасный digest и predicates. Сырой principal/DSN/private address в GitHub не нужен.

β Gate поставляет bounded operational status и способ сопоставить каждый ожидаемый процесс с его boot/config/DB evidence. Ops сопоставляет с provider inventory, start command и числом workers, включая rollout overlap. Если экземпляр не наблюдается, результат `UNKNOWN`; один случайный ответ балансировщика не представляет все реплики. Способ bootstrap-наблюдения должен работать без неучтённой DB-миграции.

### 5.4. Контракт операций и журнал

Все имена ниже — спецификация операций, а не команды, которые уже можно отправить в control issue.

| Операция | Эффект и обязательный результат |
| --- | --- |
| `observe` / `status` | Только чтение; точный scope, свежесть, health/schema/config/replicas/counts/continuity/route |
| `freeze-legacy` / `drain-legacy` | Запрет новых legacy admissions на всех процессах, ожидание/классификация уже допущенных; durable reserved/sending = 0 |
| `backup-evidence` | Проверка заранее разрешённой копии; создание копии — отдельная узкая capability, если ещё нет |
| `deploy-exact` | Только принятый release SHA/image, ожидаемые schema переходы и flags; результат включает фактический deployed SHA |
| `initialize` / `import-legacy` | Gate CLI/application API, только disabled и proven drain; сверка до/после и отсутствие дублей |
| `configure` | Только перечисленные flags/route bindings и проверенные значения; restart считается изменением эпохи |
| `serial` / `parallel` | Явная активация после свежих evidence; в canary — только его scope |
| `renew-continuity` | Обновить только evidence/expiry той же эпохи; не менять mode/generation и не оживлять stopped |
| `disable` / `stop-active` | Закрыть новые admissions; при stop-active терминально остановить активные серии и сохранить honest outcomes |
| `reconcile-operation` | Выяснить исход операции после timeout/partial failure; без слепого повтора эффекта |

Gate CLI сейчас имеет `initialize`, `import-legacy`, `status`, `serial`, `parallel`, `disable`, `stop-active`; остальные операции и wrapper требуется разработать. Флаг `--legacy-workers-drained` и произвольная строка `--continuity-evidence-ref` сами по себе не доказательства.

Каждый запрос содержит версию схемы, operation ID, release ID, target, resource/workspace scope, operation enum, exact Gate/Ops/client SHA, expected state fingerprint, intent digest, caller identity, основание разрешения, issuedAt/expiresAt. Мутабельные операции сериализованы общим target/resource lock; read-only помечает наблюдаемую эпоху.

Журнал хранит request/intent и состояния `accepted → running → succeeded/failed/partial/unknown`, стадии, before/after, timestamps и references на квитанции. До эффекта записывается intent; после — доказанный результат. Одинаковый ID и intent возвращает известный итог или продолжает reconciliation; другой intent с тем же ID отвергается. Timeout не равен «не выполнялось». Import и stop-active допускают частичные durable commits: повтор обрабатывает оставшееся, не дублирует уже выполненное. Exactly-once Telegram при неизвестном исходе не обещается.

**Хранилище раннего Ops journal:** для редких управляющих операций проектируется отдельная ветка `refs/heads/ops-gate-state-v1` существующего execution-host repository `AlphaCenter/aqub`. Это новая техническая ветка, ещё не созданная; приложение AQUB её не использует. В ней только очищенные intents, state, operation IDs, lease/fence и receipts, без секретов, переписки и персональных routing IDs. Runtime permits/quota/continuity остаются в Gate DB, а не записываются в Git на каждое сообщение.

Обновление журнала: прочитать exact tip → создать commit с единственным parent, равным этому tip → обновить ref с `force:false`. Конкурентный sibling commit не является fast-forward и отвергается; повтор сначала перечитывает состояние. Ruleset запрещает force/delete и посторонних writers; workflow не запускает application build/deploy от этой ветки. GitHub `Contents:write` имеет область репозитория, поэтому ограничение writer/refs обеспечивается reviewed workflow и ruleset, а не вымышленным branch-scoped token. Создание ветки/прав и их отрицательные тесты входят в O1a/O2 до первого provider-effect; при недоступном journal нормальные мутации запрещены.

GitHub Actions concurrency дополняет, но не заменяет этот журнал, общий со старым deploy path. **CAS в Git не является fencing Railway:** provider не проверяет Git lease. Передача права конфликтующей мутации требует terminal/reconciled прежнего execution и его provider requests; одного TTL недостаточно. `UNKNOWN` блокирует новую конфликтующую мутацию. Lost lease запрещает executor новые эффекты; аварийный stop имеет отдельную процедуру §10 с проверкой, что pending deployment не восстановил отправку.

Receipt содержит точный scope, run/operation/release IDs, source/deployment/process/config/schema, время/срок доказательства, counts, выполненные predicates, доказанные effects/postconditions и stable error code. `UNKNOWN` не превращается в ноль. Внешняя проверка результата не ограничивается exit code команды.

## 6. Обязательные доработки Gate

### G1. Контракт управления, bootstrap и безопасный переход

β Gate:

- исправляет порядок миграции в обоих specs #716/#718 и runbook;
- выделяет application boundary общего управления для CLI и выбранного transport;
- отделяет control runtime/configuration от Telegram transport и token-required Settings: текущий constructor получает `bot_resource` из `telegram_bot_token`. Control-процесс должен получать проверенный несекретный bot resource identity из runtime evidence/контракта и сверять его, не требуя настоящий или фиктивный Telegram token;
- возвращает schema-valid redacted status/error, проверяет workspace/schema и происхождение evidence;
- обеспечивает необходимую baseline-наблюдаемость до 0112;
- интегрирует operation ID/idempotency/reconciliation с Ops;
- исправляет ссылку `#undefined` в #716 на #715;
- доказывает совместимость safe mode с новой schema и сохранёнными outcomes.

В release package перечисляются **все** необходимые миграции нового кандидата. Нельзя обещать «только 0112», если continuity/canary/journal потребовали ещё таблицы. Ранее слитые миграции не переписываются; дополнительные изменения — новые additive revisions и проверенный переход с фактического baseline.

### G2. Постоянная работа и stop при потере входящих

В текущем #720 healthy admission истекает не позднее часа; `serial/parallel` повышают generation. Новый claim обновляет generation серии, поэтому повтор команды не обязательно ломает её между сообщениями. Однако уже выданный claim может быть отвергнут при гонке; бесшовное renewal таким способом не доказано. Проверка здоровья должна быть отдельной операцией.

Требуется встроенный автоматический supervisor Gate:

- начальное evidence задаёт verified epoch: полный состав ingress процессов, boot IDs, connector/account binding, права, конфигурацию webhook и очереди приёма;
- в пределах эпохи проверяет durable receipts/backlog, ошибки/dead-letter, работу проекции, connector changes, process heartbeat и допустимые provider-сигналы. Отсутствие новых сообщений само по себе не доказывает непрерывность;
- нормальный цикл renewal — не реже 5 минут; выданный evidence живёт не более 1 часа; продление возможно только до текущего expiry и при всех нужных predicates;
- один действующий renewer на scope либо CAS по evidence version; mode/generation активной серии не меняются от здорового renewal;
- restart, изменение прав/connection, неизвестный разрыв, expiry или неполный inventory закрывают admission немедленно при обнаружении. Supervisor терминально останавливает затронутые active серии и создаёт видимый reason; при временной недоступности БД admission остаётся закрытым, stop завершается после восстановления;
- после фактического разрыва нужно новое подтверждение оставшихся текстов. Renewal не разрешает возобновление прежней серии;
- обновление mode/config выполняется отдельно, с новым поколением и определённой судьбой старых series/claims.

Принятие: активная длинная серия проходит несколько renewal без смены generation; сценарий длительностью более часа не зависает. Реальный gap и expiry проверяются отдельно и не маскируются автоматическим `healthy=true`. Допустимые доказательства Telegram не дают абсолютной гарантии доставки каждого webhook: известные ограничения честно отражаются в контракте.

### G3. Клиент ChatGPT и уведомления Марку

Gate M/подключённый Work должен получить актуальную schema и показывать понятные результаты:

1. Читает последний контекст с `sequence_approval.ready=true` и ненулевым `dialog_inbound_revision`.
2. Показывает тексты, порядок, RU/BY и адресата; получает подтверждение.
3. Передаёт `expected_inbound_revision` именно подтверждённого контекста. Не подставляет новую revision под старое согласие.
4. При pending projection ждёт обработки и перечитывает контекст; stale/rebind/changed texts требуют нового подтверждения.
5. Различает queued и sent. В readback обходит все страницы; показывает `draft_text_matches_approval=false/null`, если сохранённый текст изменён или отсутствует. Не представляет его неизменяемым архивом approval.

β Gate проверяет resolver уведомлений: account permission ↔ authenticated principal Марка, ровно одна enabled Business connection, согласованные owner account/connection/private chat, канал Марка отличается от получателя серии. Ops фиксирует фактическую привязку по существующему permissions-контракту; IDs не перекладываются на Марка.

Stop коммитится независимо от доставки уведомления. `blocked_route`, `failed`, `unknown` сохраняются и видны; unknown notification не повторяется автоматически. Known 429 retries учитываются в общей provider-политике и в canary quota. Уведомление не содержит входящее сообщение собеседника. Недоступность канала уведомления не отменяет остановку.

### G4. Технически ограниченный canary

До Production отправок нужен серверный admission scope: `execution_id`, exact workspace/accounts/dialogs/principal, разрешённые draft/body hashes, notification destination/template, expiry, mode transition и общий счётчик попыток.

Каждый provider send, включая notification/retry, **до вызова HTTP** атомарно резервирует одну попытку из общего лимита. Резерв не возвращается при неизвестном исходе. Crash после резерва может уменьшить доступный бюджет, но не превысить его. Scope и счётчик переживают рестарт и смену serial/parallel. Все остальные sequence admissions этого workspace во время canary закрыты. Notification backlog других execution тоже не должен уйти при включении worker.

По expiry/cap/ошибке новый допуск закрывается; незавершённый canary не превращается в обычную Production серию. Его недоставленный notification outbox также не должен ожить после возвращения обычного режима. Изменить scope или увеличить бюджет тем же execution ID нельзя. Continuity renewal не продлевает canary deadline/quota. Режим приёмки не заменяет обычное подтверждение текстов Марком.

## 7. Обязательные доработки Ops

### O1. Фактическая конфигурация и capability probe

Пакет состоит из двух последовательных частей, чтобы не создавать зависимость live-проверки от ещё не написанного полного executor:

1. **O1a/G1a:** offline разработать минимальный probe, Gate-specific scope, безопасную диагностику #338 и, если нужна, baseline bootstrap-версию без schema delta. Проверить fixture/CI и независимо принять точные SHA этого малого пакета.
2. **O1b:** по отдельному ограниченному плану выполнить read-only наблюдение; при необходимости отдельно разрешённую baseline-публикацию bootstrap. Это не миграция 0112, не активация серий и не canary. Получить live proof и выбрать transport. После этого достраивать основной executor и финальный release package.

Этот будущий ранний этап требует своей проверки и конкретного разрешения для baseline-публикации. Он не ждёт готовности полного P4 и не означает разрешения выполнять его в ходе написания ТЗ. Перед окончательным cutover наблюдение повторяется для свежести.

O1b должен закончиться заполненным Gate release manifest, а не новой просьбой Марку выяснить БД:

- actual provider/runtime/DB binding, schema, database/role scope и наличие общих соседей;
- выбранный transport из §5 и первый успешный bounded status probe;
- полный inventory web/legacy/new workers и способ доказать drain;
- auto-deploy/pending deploy/config changes и общий lock;
- backup method и recovery scope;
- pool semantics и connection budget;
- разрешённый механизм привязки аккаунта/канала Марка.

Неизвестность превращается в конкретный результат probe с кодом, ответственным и выбранной альтернативной веткой. Непроверенная гипотеза не записывается как `ready`.

Ops #338: получить безопасную диагностику формы ответа `environment-config` — только названия разрешённых полей/типы/наличие и stable parser stage, без значения переменных. По ней исправить конкретный adapter/parser и добавить fixture regression. Повторный полноценный preflight после reviewed изменения должен завершиться валидной квитанцией. Узкий observer #337 не заменяет неисправный полный preflight. Исторический сбой сам по себе не повод менять Gate DB.

### O2. Scope, исполнитель, полномочия и квитанции

Ops реализует §5, Gate-specific target/предикаты и общий lock. Только Ops core/action/manifest PR и отдельный client pin PR в существующем execution host. AQUB application не меняется. Для каждого изменения фиксируются source/client/action/workflow digests.

Read-only и mutation paths различаются. Machine requester создаёт план; действующее правило отдельного authenticated approver сохраняется. Проверка автора комментария подтверждает GitHub identity, но не заменяет вердикт δ Gate. Аргументы пользователя не превращаются в shell/SQL.

Если provider может читать переменную по ключу — запрашивать только нужные ключи. Если API выдаёт весь набор, это допускается только в ограниченном credential-bearing процессе с запрещёнными raw stdout/errors/debug artifacts и негативными тестами redaction. Отчёт содержит predicates вместо значений.

### O3. Конфигурация, backup, точная публикация и аварийный stop

Allowlist runtime flags:

- `GATE_REPLY_SEQUENCE_WORKER_ENABLED`;
- `GATE_REPLY_SEQUENCE_STOP_ON_INBOUND_ENABLED`;
- `GATE_REPLY_SEQUENCE_DISPATCH_V2_ENABLED`;
- `GATE_REPLY_SEQUENCE_PARALLEL_ENABLED`;
- `GATE_REPLY_SEQUENCE_NOTIFICATIONS_ENABLED`;
- `GATE_REPLY_SEQUENCE_DB_POOL_MODE`.

Новые G2/G4 настройки, если они нужны, добавляются отдельными типизированными полями reviewed контракта. Не разрешается универсальный setter любых variables. Значения по всем репликам проверяются после restart. Лимиты inflight автоматически не повышаются.

Проверка соединений: direct/session pooling; transaction pooling не подходит для используемых session advisory guards. Бюджет включает все процессы/реплики и overlap: локальные sender guard connections + 2 ingress guards на процесс + ordinary pool + CLI/monitoring. Минимум 2 ordinary connections сохраняются для ingress/health/recovery. Сумма должна укладываться в подтверждённый потолок PostgreSQL; при нехватке сокращаются concurrency/replicas по плану, не повышается потолок без решения.

`deploy-exact` проверяет полный immutable SHA и migration graph. Existing fast-deploy публикует current main и не обеспечивает эту процедуру сам по себе. Перед merge кандидата проверяется, не запустит ли auto-deploy миграцию; при наличии автопубликации её ограничение и верификация входят в план до merge. Merge, deployment и activation — три отдельных состояния.

## 8. Backup и восстановление без фиктивных гарантий

### Обязательный backup contract

До первой DB-миграции Ops фиксирует:

- точную БД/service/volume и список других databases на общем ресурсе;
- конкретный поддерживаемый способ копии, её ID, completion time, размер/целостность, срок хранения и защиту от удаления;
- schema/release, к которым относится копия;
- фактический момент восстановления данных (RPO) и измеренное/расчётное время восстановления (RTO);
- изолированный restore drill тем же механизмом на синтетическом наборе, проверку схемы, counts и запуска с worker off;
- процедуру доступа к защищённой копии и проверку её пригодности без выгрузки пользовательских данных в GitHub artifacts.

Основной выбор O1 — существующая пригодная volume backup capability с completed/locked evidence. Если она недоступна или scope общий и неприемлем, Ops готовит узкий logical backup только фактической Gate DB с шифрованным хранилищем и restore drill. При доступном проверенном TCP используется этот transport. При private-only БД требуется отдельная фиксированная in-network backup capability; operations endpoint из §5.2 сам по себе её не предоставляет. Нет пригодной volume copy и нет проверенного logical backup — результат `BLOCKED_BACKUP`, R4 запрещён. Это заранее определённая ветка O1/O3, а не разрешение открыть БД или добавить произвольный command. Возможность метода доказывается до миграции; generic SQL/restore/delete не добавляются.

Для этого выпуска целевой pre-migration backup создаётся после drain и до migration. Копия удерживается до завершения периода наблюдения и принятого recovery window, минимум 7 суток. Если сервис не поддерживает требуемое удержание, O1 обязан выбрать работоспособный метод и явно зафиксировать это до разрешения изменения.

Резервная копия, сделанная до миграции, **не даёт нулевую потерю входящих после своего timestamp**. RPO на момент аварии показывается явно; уже отправленные Telegram сообщения откатом БД не отменяются. Исходящие остаются disabled после restore, история попыток сверяется с сохранённым журналом. Общий volume restore затрагивает всех его потребителей и не называется «откатом только Gate».

Railway volume snapshot и PITR — разные методы. Snapshot restore имеет ограничения project/environment; включение PITR может менять ресурсы/настройки и перезапускать БД. Ни один метод не объявляется уже разрешённой операцией только потому, что он описан у провайдера. Drill использует отдельный disposable scope и не восстанавливает поверх Production.

### Основное восстановление после неудачного выпуска

Первый путь — **закрыть допуск, остановить worker, сохранить ingress/readback и исправить код на совместимой schema**. Возврат legacy binary после canonical import не является готовым rollback. Downgrade/drop 0112 и последующих durable таблиц в Production не входят в этот выпуск.

Восстановление данных — отдельный аварийный план с точной копией, изолированным восстановлением, сверкой outcomes, оценкой потерь и явным решением Марка по затрагиваемому scope. Автоматического restore Production нет.

| R7. Ограниченная приёмка | Exact canary: serial stop+notification, затем parallel; общий scope/cap/TTL | Доказанные delivery/stop/notification и independent progress, итог ≤6 attempts | Disable/stop; текущая попытка не принята; бюджет не расширяется |
| R8. Длительная работа | Проверка автоматического renewal, bounded наблюдение реального ingress без дополнительных send; анализ состояний | >1h, минимум два успешных renewal, стабильные generation/эпоха, нет stale/unknown new attempts | При gap stop; новая приёмка затронутого исправления |
| R9. Обычный режим | δ Gate оценивает release evidence; α Gate принимает продукт; отдельный exact plan снимает canary restriction | Обычные свежие user approvals работают; Ops status/recovery доступны | Сохранить ограниченный/disabled режим |
| R10. Закрытие | Единый ledger, актуальные инструкции, принятые evidence и передача эксплуатации | Definition of Done из §12 | Задачи остаются открытыми по фактическому остатку |

Миграция в `railway.toml` запускается **до старта нового приложения**. Поэтому R2/R3 обязательны до R4, а не после него. Дополнительный ручной `alembic upgrade head` после успешного preDeploy не считается отдельным обязательным этапом; повтор допустим только как verified no-op/reconciliation.

Importer сохраняет исторические unknown. Историческая stopped/legacy_reapproval_required серия тоже остаётся в БД. Эти записи не требуется обнулять перед activation. Блокеры — текущие живые attempts, неразрешённые active permits/claims, несогласованные memberships/authority. Quarantine классифицируется: unsafe ambiguity требует разбора; терминальная изолированная история с доказанной невозможностью отправки не блокирует весь workspace бесконечно.

В этом ТЗ capability-флаг PARALLEL_ENABLED=true устанавливается до canary при DB mode disabled. Фактическую одновременность выбирает DB mode: serial допускает один slot даже при таком флаге. Перед serial → parallel A и её notification должны быть terminal, occupied/quarantined текущей попытки = 0; выполняется disable → parallel без изменения flags и без restart. Это заменяет старую последовательность runbook с перезапуском между фазами. Любой незапланированный restart всё равно инвалидирует evidence и прекращает текущую попытку canary.

## 10. Аварийная остановка и поведение на ошибках

Для активации нужен полный свежий preflight. **Для уменьшения активности нужны меньшие, отдельно проверяемые условия:** авторизованный запрос, точная цель и совместимая stop-операция. Stop получает приоритет через отдельный fence/CAS, а не ожидает обычный mutation lock. Нездоровый notification route, новый source SHA или неполный обычный health не должны сами по себе запрещать stop.

Emergency CAS повышает durable stop fence/эпоху. Нормальный executor и старый fast-deploy сверяют fence перед каждым новым эффектом и теряют право включать отправку. Уже начатая provider-операция или миграция не объявляется отменённой: выясняется исход, следующие стадии блокируются. Provider API не обеспечивает атомарность между чтением fence и своим эффектом; Ops обязан учесть pending rollout, отменить его поддерживаемым способом либо дождаться/сверить и повторно применить stop. `STOPPED` выдаётся только после доказанного отсутствия процесса/деплоя, способного вернуть отправку. При недоступном journal/DB ограниченный provider-stop возможен через действующий защищённый executor с честным `UNKNOWN` до полной сверки. Если GitHub/Actions полностью недоступны, новый workflow не запустится: действует автономное закрытие допуска Gate, после восстановления завершаются stop/reconciliation. Несуществующий резервный пульт не обещается.

1. При доступной БД `disable` атомарно закрывает новые admissions; `stop-active` фиксирует терминальную остановку под нужными dialog barriers. Postcondition читается заново.
2. Ops выключает dispatch worker на всех репликах и проверяет отсутствие живых отправителей. Уже допущенные HTTP-запросы получают фактический исход; неизвестное сохраняется.
3. Если БД недоступна, используется заранее проверенная ограниченная provider-операция остановки worker/runtime. Если workers живут в одном процессе с ingress и отдельно остановить их нельзя, крайний путь — остановить точно Gate service; это прервёт ingress. Последствие фиксируется, после восстановления нужны новая continuity и новые approvals. Нельзя обещать сохранение ingress при такой топологии.
4. После частичной остановки status показывает, что подтверждено и что ещё неизвестно. До доказанного отсутствия новых sends нельзя писать `STOPPED`.
5. При старом коде, rollback drift или неподдерживаемой schema контроль не пытается выполнить несовместимый SQL: используется проверенный provider-stop и дальнейшее восстановление.

| Сбой | Обязательное поведение |
| --- | --- |
| 429 | Остановить данную серию, сохранить общие cooldown; соседям ждать только занятый ресурс |
| Timeout/5xx/потеря соединения при отправке | Unknown, tail stopped, без автоматического resend |
| Потеря guard connection/процесс не завершил HTTP | Закрыть admission, удержать/quarantine permit; TTL не доказывает, что запрос исчез |
| Duplicate inbound | Один логический stop, без повторного исходящего сообщения |
| Notification failure | Stop сохранён, failure/unknown виден; канал уведомления не условие emergency stop |
| Failure после части import/stop | Журнал partial; reconciliation и идемпотентное завершение оставшегося |
| Config/source drift во время операции | Не начинать новые эффекты; re-observe, stop при необходимости; не доверять старому plan |
| Исчерпан canary cap/TTL | Запрет следующего provider call, завершение тестовой попытки; обычный режим не включается |

### 11.2. Конкретный план Production-проверки

Бюджет прежнего плана сохраняется: **не более 6 outbound Telegram send attempts суммарно, максимум 10 минут, LLM calls = 0, не более 1 отдельного read-only вызова webhook-info провайдера**. Это проект будущей проверки, не разрешение отправлять сейчас.

α Gate заранее получает из фактической установки и фиксирует приватно exact refs разрешённых тестовых диалогов для трёх серий A/B/C, RU/BY bindings, учётной записи и канала Марка, texts/body hashes и ingress test actor. A и B могут использовать один RU-диалог после terminal stop A, обработки нового inbound и нового подтверждения B; для B/C нужны два независимых маршрута. Нельзя брать случайных реальных собеседников. B/C не должны быть встречными RU→BY и BY→RU диалогами, в которых исходящая одной серии становится входящей другой. Если подходящих контролируемых Марком диалогов нет, α Gate оформляет их подготовку как конкретный шаг, не предполагая автоматического разрешения создавать новые аккаунты. Ops не подменяет их историческими контактами. Марк подтверждает конкретные тексты и адресатов одним ограниченным планом.

| Шаг | Действие | Максимум outbound attempts при успешном сценарии |
| --- | --- | --- |
| C1, serial | RU, серия A из 2 текстов; первое доставлено; разрешённый тестовый собеседник присылает inbound до второго | 1 |
| C2 | Tail A stopped; Марк получает уведомление; readback показывает сохранённый второй текст | 1 notification |
| C3 | Убедиться: A и notification terminal, occupied/quarantined=0; disable → DB mode parallel на тех же flags/репликах; сохранить epoch/cap/execution ID | 0 |
| C4, parallel | B на RU и C на BY, по 2 текста; обе серии прогрессируют независимо, вторые ≥60s после первых | 4 |
| C5 | Закрыть canary admission; сверить outcomes, остатки, counts, quota и отсутствие sends вне scope | 0 |

Итого **5 сообщений серий + 1 уведомление = 6**. Тестовый inbound инициирует согласованный участник обычным Telegram-клиентом. Если отправить его через Gate, получится седьмая попытка, что запрещено этим планом. Подстановка записи в БД или ручной POST webhook не доказывают реальный Telegram ingress. Чтение состояния не расходует send quota. Тексты/персональные IDs не помещаются в публичную квитанцию.

429 retry notification расходует тот же общий бюджет и может не оставить попыток на завершение матрицы. В этом случае canary не принят; лимит не увеличивается, прежние попытки не обнуляются. Unknown тоже завершает проверку без resend. Новый live canary требует нового точного разрешения, а не автоматического rerun.

10 минут отсчитываются от выдачи допуска serial до первой queue/отправки C1 и включают C3. Подготовка образов/backup/flags и все плановые рестарты выполняются до этого окна с закрытой отправкой. Один разрешённый webhook-info call учитывается во всём конкретном release/canary execution; перенос до T0 не создаёт второй бюджет. Continuity renewal в течение этого окна использует проверенные внутренние сигналы; если для доказательства потребуется ещё provider call, проверка останавливается без расширения scope. Незавершённый за 10 минут план не принят; часы и quota не сбрасываются.

Полный сценарий stop для BY и искусственные 429/timeout проверяются в staging; шесть Production попыток не дают права заявить, что все fault cases проверены live. Строгое перекрытие двух HTTP подтверждается детерминированным A03; live проверка доказывает независимый прогресс, limits и реальные delivery outcomes.

После C5 следует R8: наблюдение не менее 65 минут с автоматическим renewal при закрытой отправке, без дополнительных тестовых send. Максимум один webhook-info call относится к этому же live execution, включая R8. Алгоритм renewal на допустимых локальных evidence проверяется в staging заранее; если он требует повторных provider reads, данный ограниченный план неисполним и должен быть переработан до запуска с явным решением по новому scope. Лимит сам не повышается. Receipt R8 доказывает renewals на живом runtime при закрытой отправке. Прохождение активной серии через >1h доказывает A10 в staging; idle-наблюдение его не подменяет. Просроченные canary drafts/outbox не возобновляются.

### 11.3. Вердикты

- **Технически принято:** exact Gate/Ops/client package прошёл свои gates и независимую проверку.
- **Переход выполнен:** точные runtime/schema/import/config и postconditions подтверждены квитанциями.
- **Пробная отправка принята:** C1–C5 в пределах разрешения, без неизвестного/вне scope.
- **Продукт принят:** α Gate после δ Gate подтверждает весь пользовательский путь, включая реальный клиент и постоянную работу.

Один зелёный build, закрытая задача или успешный deploy не заменяет остальные состояния.

## 14. Эксплуатация после приёмки

Gate supervisor постоянно проверяет admission/continuity и закрывает небезопасную отправку без ожидания человека. Status показывает mode/generation/epoch/expiry, queue age, last progress, active/sending/unknown/quarantined counts и состояние уведомлений. Loop heartbeat сам по себе не доказывает продвижение очереди.

Ops получает actionable причину и ссылки на operation/release evidence. В incident первым действием является предусмотренный stop, затем reconciliation и исправление; очистка history/permits для зелёного health запрещена. Для Марка сообщение описывает, какие серии остановлены, что отправлено/неизвестно и что требует нового подтверждения.

Обновление source/config/replicas/Business connection проходит тот же ограниченный lifecycle: disabled/drain по необходимости → exact change → новая continuity → явная активация. Бесшовное здоровое renewal выделено отдельно и не перезапускает этот lifecycle каждые пять минут.

Release ledger хранится в Ops #336 и связанной карточке Gate: package versions, verdicts, последний доказанный этап, ссылки/дигесты квитанций и конкретный остаток. Старые статусы помечаются историческими. ### Официальная документация provider, проверена 28.09.2026

- [Railway run](https://docs.railway.com/cli/run): локальное исполнение.
- [Railway SSH](https://docs.railway.com/cli/ssh): отдельные SSH keys; project token не поддерживает управление ключами.
- [Pre-deploy](https://docs.railway.com/deployments/pre-deploy-command): private network и service env, отдельный контейнер, без volume, failure блокирует deployment.
- [Volume backups](https://docs.railway.com/volumes/backups), [PITR](https://docs.railway.com/volumes/point-in-time-recovery), [volume API](https://docs.railway.com/integrations/api/manage-volumes): поддерживаемые возможности не равны готовой Ops capability.
- [GitHub Git references](https://docs.github.com/en/rest/git/refs#update-a-reference): `force:false` требует fast-forward. Предложенный single-parent CAS — проектное применение этого правила; он не даёт provider fencing.

**Ограничения:** фактический Gate DB service, TLS transport, usable backup, полный runtime inventory, live notification route и точные тестовые диалоги пока не подтверждены. Они не угаданы и не переданы на выяснение Марку: для каждого назначены пакет, исполнитель, доказательство и ветка решения. Полнота ТЗ означает описанный путь к результату и обработку известных развилок; она не означает, что ещё не выполненные Production-проверки уже прошли.
